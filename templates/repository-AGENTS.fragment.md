# Codex GitHub 单任务或单阶段治理接入片段

把本片段合并到目标仓库现有根 `AGENTS.md`，保留原有项目规则。

## 本机治理来源

通过工具只读定位本机绑定：非空的 `CODEX_GOVERNANCE_CONFIG` 指定文件，否则读取
`${XDG_CONFIG_HOME:-$HOME/.config}/codex-governance/local.toml`。该文件由代理读取，不是 Codex 原生配置层。
从 `paths.source_root` 取得治理源仓库的实际绝对路径；以下文件均相对该根目录读取。
这一步只定位规则；普通任务不因此执行身份核验或 GitHub 治理。不要把真实本机路径或绑定写入本文件。

## Codex 治理声明

- 通用工程原则遵守 `governance/engineering-principles.md`，普通开发同样适用。
- 只有用户在当前消息中显式调用 `codex-stage-orchestrator` 并给出明确开发需求时，才启用
  `governance/codex-development-governance.md`。
  未显式调用或用户明确禁止时不启用；仅提及、询问或修改 Skill、历史调用及启动 Profile 均不算显式调用。
  未启用时按用户授权处理，不因本治理核验身份、查询或创建 Issue、派生治理角色。
- 同一已授权任务的澄清与继续执行沿用授权；新任务或下一阶段需重新显式调用。准确 Issue 由主会话
  在当前仓库定位或创建，下游角色只接收已确定对象；多个候选或语义不明时由用户决定。
- 确认启用后，主会话与各角色先按各自入口读取本机绑定并执行身份核验，再读取治理规范，按第三节读取工程原则、
  第六节执行职责与交付边界；身份细则统一遵守第四节。角色独立性构成顺序派生
  `scope-planner -> implementer -> reviewer` 的理由，同一共享路径只有一个实现者。
- 命令权限不扩大职责、身份、任务范围或破坏性授权；规划与审查角色保持被审对象只读。
  当前精确 PR 头获正式批准且没有阻塞反馈时才合并，不使用管理员绕过。
- 主会话清理前必须读取
  `skills/codex-stage-orchestrator/references/stage-procedure.md` 第五节，
  完整执行归属、现场保留、准确引用及条件删除要求；清理失败保留现场并请用户裁决。
  清理完成后才关闭 Issue 或推进其中已批准任务，PR 关联方式按治理规范第六节。
- 当前任务或阶段完成后更新适用上层 Issue 并停止，不创建、选择、激活或签发下一阶段或模块。
  这项推进边界优先于通用治理的后续模块安排。
- 本治理不修改其他治理工具的配置、服务或认证材料；不同编排者不得同时治理同一 Issue。
- 公开证据与私有路径交接遵守治理规范第三节，不公开本机绑定或工作站路径。
