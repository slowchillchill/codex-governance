## 本机治理来源

通过工具只读定位本机绑定：非空的 `CODEX_GOVERNANCE_CONFIG` 指定文件，否则读取
`${XDG_CONFIG_HOME:-$HOME/.config}/codex-governance/local.toml`。该文件由代理读取，不是 Codex 原生配置层。
从 `paths.source_root` 取得治理源仓库的实际绝对路径；以下文件均相对该根目录读取。
这一步只定位规则；未启用治理的任务不因此执行身份核验或 GitHub 治理。不要把真实本机路径或绑定写入本文件。

## Codex 治理声明

- 通用工程原则遵守 `governance/engineering-principles.md`，普通开发与研究中适用的工作同样遵守。
  按第四节“验证结果与交付推进”在必要验证未通过时停止受影响的交付动作，当前授权内修复并验证通过后
  恢复；会话恢复同样适用，不以记录失败或已有批准代替通过。
  执行偏差、错误与困难按第五节“执行偏差与异常处理”核对方案与校验依据、联网查证，并遵守停止汇报条件。
  触及第七节规定的设计变更时，按“提交前独立内容审查”审查待提交候选，通过后才提交；未启用治理的任务
  同样适用，不因此启用 GitHub 治理。
  构建产物与证据生命周期遵守该文件第六节；需要使用备份盘而发现其不可用时，立即停止当前任务并
  向用户汇报，等待裁决。
- 用户显式调用 `codex-stage-orchestrator` 并给出明确开发需求，或接收流程按 `governance/group-collaboration.md` 接受已获用户授权的决策／研究组准确任务委托时，才启用
  `governance/codex-development-governance.md`。
  未显式调用且未接受有效委托，或用户明确禁止时不启用；仅提及、询问或修改 Skill、历史调用及启动 Profile 均不算显式调用。
  未启用时按用户授权处理，不因本治理核验身份、查询或创建 Issue、派生治理角色。
- `codex-strategy-research` 按其自身入口和当前授权启用；本片段不安装或启用研究流程。双方分工读取
  治理规范第一节“与策略研究的分工”；工程三角色顺序只用于工程任务。
  研究来源工程需求的接收、验证和返回读取第六节“研究来源需求的接收与验证”及“工程交付返回研究”。
  双方各自维护所属任务；研究可直接签发授权内必要工程依赖，PR 由实际签发组创建。开发组所有角色与技术平台操作共用 `github.development`，完成结果固定回签发组；不自动恢复研究或关闭来源任务。
- 同一已授权交付的澄清与继续执行沿用授权；范围外新任务需重新显式调用或接受新的有效委托。
- 确认启用后，主会话与各角色先按各自入口读取本机绑定并执行身份核验，再读取治理规范，按第三节读取工程原则、
  第六节执行职责与交付边界；身份细则统一遵守第四节。角色独立性构成首次按
  `scope-planner -> implementer -> reviewer` 顺序派生的理由，同一共享路径只有一个实现者。
  主会话可在同一实现者和审查者之间继续交接，候选审查与正式 Review 的条件读取第六节。
- 命令权限不扩大职责、身份、任务范围或破坏性授权；规划与审查角色保持被审对象只读。
  不使用管理员绕过。
- 准确 Issue 的定位与父交付授权读取治理规范第二节，Project 接入与同步读取第五节，失败分流、
  PR 关联、合并与关闭读取第六节。主会话清理前必须读取
  `skills/codex-stage-orchestrator/references/stage-procedure.md` 第五节并执行适用步骤。
- 本治理不修改其他治理工具的配置、服务或认证材料；不同编排者不得同时治理同一 Issue。
- 公开证据与私有路径交接遵守治理规范第三节，不公开本机绑定或工作站路径。
