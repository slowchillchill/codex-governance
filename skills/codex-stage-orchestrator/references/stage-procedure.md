# 任务与父交付编排程序

本程序给出交接与具体操作路径；主会话执行前必须已读取
[治理规范](../../../governance/codex-development-governance.md)。启用、身份、授权及交付判定以该规范为准，
下文按其章节引用；公开证据与私有路径交接遵守第三节，完整清理步骤保留在第五节。

## 1. 确定 Issue 并恢复事实

按规范第二节确认启用后，依第四节只读解析本机绑定、内联绑定的 `GH_CONFIG_DIR` 核验身份，再按第二、
五节定位准确交付 Issue 与执行 Issue，回读当前合同、GitHub 与本地状态，恢复已有候选、提交、验证及审查证据。
需要代码探索时，按规范第四节选用实际工作树对应的代码索引，交接工作目录、适用源码版本及本轮相关缺口。

已明确指定 Project 时，用 `gh project view`、`field-list`、`item-list` 或 GraphQL 读取实际项目、条目、
字段和选项；查询须覆盖目标条目，不能把分页未读完当成不存在。关联前查询已有条目，缺少时才用
`gh project item-add` 关联当前 Issue；更新用 `item-edit` 的实际项目、条目、字段与选项标识。
这些认证命令继续内联控制账号绑定目录；写入结果不明先回读，权限与同步缺口按规范第五节处理。
接口用法见 [GitHub CLI](https://cli.github.com/manual/gh_project_item-edit) 与
[原生父子 Issue API](https://docs.github.com/en/rest/issues/sub-issues)。

## 2. 规划当前任务

按规范第六节“范围规划”定位本轮相关的项目决策引用。派生 `scope-planner`，交付准确交付 Issue、执行
Issue、本轮任务、适用合同、相关项目决策引用、必要 Project 引用和工作目录。角色先核验身份，再返回
该节要求的范围建议与决策缺口；主会话核对依据并按该节处理，更新当前合同后交付实施范围。

## 3. 实施当前任务

派生 `implementer`，交付执行 Issue 中分配给本轮的任务、已批准范围、非目标、验收、工作目录和已有现场。
角色先核验身份，按规范第六节“实现”实施、自审和验证，再向主会话交付适用的完整待提交候选，或 PR、
实现头、差异与验证结果；候选转交第四节。候选审查、失败与缺口按规范第六节处理，通过所需前置后才提交与推送。
按规范第四节和第六节“实现”交接索引情况、证据入口、产物及工作树归属、仍需保留对象；必要证据归档
与产物清理执行下文第五节。PR 按规范第六节仅使用 `Refs`，主会话回读真实状态后组织下一次交接。

## 4. 独立内容审查与正式 Review

派生 `reviewer`，按规范第六节“独立审查与正式 Review”交付本轮任务、适用合同、准确工作目录和验证证据。
审查候选时交付 Git 基线与完整待提交差异，区分暂存区和工作区、覆盖新增与删除文件；实现者停止写入，
审查者只读返回内容结论。主会话按“失败与审查反馈分流”组织同一实现者修正、验证及同一审查者补审。
审查 PR 时交付实际比较基准、当前头及适用候选结论；审查者按该节核对内容与后置检查，并提交显式绑定
已审 `commit_id` 的正式 Review。主会话回读 Review、当前版本及依据，再按第六节决定返工或合并。

## 5. 合并与收尾

主会话按规范第六节“合并门”回读当前头、Review、阻塞反馈、必需检查和合同依据，
仅在本轮合同成立、必要验证与验收通过、精确头正式批准且无未解决阻塞时，以
`--merge --match-head-commit <SHA>` 普通合并；批准不能覆盖失败或证据缺口。

合并动作不得同时删除远端任务分支。合并后先回读 GitHub，证明 PR 已合并，再按下述步骤同步本地主
工作树并完成适用清理；没有任务专用工作树也须处理主工作树同步。

### 证据归档与产物清理

本小节的方法也适用于实现者开发期间的产物管理和审查前证据整理；工作树与分支删除仍只按合并后的
“清理本轮任务对象”执行。证据范围、保留期限和报告要求统一遵守工程准则第六节“构建产物与证据生命周期”。

1. 根据本轮实际构建命令、配置与交接确认准确输出路径、归属和占用，覆盖工作树内外的输出，不默认
   所有产物都在 `target`。读取必要文件清单，区分可删除产物、必要证据、交付物和不明内容；核对实际
   路径、符号链接及共享使用情况，不能把链接目标或相邻目录一并当成本任务对象。不得删除未提交源码、
   用户原有材料、归属不明内容或仍被使用的对象。
2. 将核心证据独立保存到现有交付记录或已授权的仓库外归档位置。使用备份盘时按治理规范第四节唯一
   匹配当前仓库的私有绑定，核对实际挂载及目标文件系统、可用空间；目录存在不能代替挂载核对。
   此时或归档过程中发现备份盘不可用，按工程准则第六节立即停止当前任务并向用户汇报，等待裁决；
   下游角色停止并返回主会话，由主会话汇报。不得继续后续归档或局部清理，也不自行重试或更换位置。
   在归档根下按任务与准确源码版本选择不覆盖既有材料的位置，同一版本的不同验证结果也不相互覆盖。
   复制前停止源材料写入，只复制必要材料，不打包整个构建目录；核对完成前保持源材料不变。
   归档根中已有的备份不进入本轮清理范围。
3. 按工程准则核对复制的文件集合、内容完整性和可读取性；压缩包须能解包读取，链接
   须不依赖将被删除的源文件。失败时保留源材料，不反复覆盖已有有效归档。核对成功后更新原证据入口，
   在现有 PR 或交付记录中保留版本、必要结果及不含私有路径的归档相对位置；实际根目录在私有交接中
   传递。确认后续审查者可访问所需材料，不能只给一个不可读取的入口。正式交付物如需保留，同样先按
   交付要求保存，不能因可重建而删除唯一交付副本。
4. 对已经核实、停止使用且不承载唯一必要证据的本轮产物执行清理。先明确准确删除清单，再使用能限定
   到该清单的构建工具清理能力；工具会连带删除证据或共享输出时，改为按准确清单逐项删除文件及已经
   清空的本任务专用目录。不使用通配符、宽泛递归删除、`git clean`，也不删除主工作树或修改 Git 引用。
   这项产物清理不要求先删除工作树；部分对象不明时保留受影响对象，未触发备份盘不可用的暂停要求时，
   其他已独立核实的可删除产物仍可清理。无法安全分离时保留该范围并报告，不推断可以整体删除。
5. 在现有交接或收尾报告中记录证据入口、已清理对象、实际释放量及其测量依据、遗留对象与原因和后续
   处理条件；并发磁盘写入等使释放量无法可靠测得时说明限制。不把局部清理写成工作树收尾完成，也不
   绕过下文的 Issue 关闭与推进条件。后续完整删除工作树前仍须重新核对当时的现场。

### 同步本地主工作树

1. 从已合并 PR 的目标仓库与当前远端默认分支事实，确认要同步的准确远端和默认分支，不假定远端叫
   `origin` 或分支叫 `main`，也不以 PR 头仓库代替目标仓库。结合项目入口及
   `git worktree list --porcelain` 定位日常使用的主工作树，确认其实际检出该默认分支，读取当前 HEAD、
   `git status --short --branch`、必要差异及进行中的 Git 操作。路径、分支或远端无法确认、主路径检出
   其他分支、存在冲突或活动 Git 操作时保留现场并报告具体缺口，不自动切换分支或解除锁与占用。
2. 核对 `remote.<准确远端>.fetch` 中该默认分支实际对应的远端跟踪引用；抓取时保留这项映射，避免主工作树
   快进后对应远端跟踪引用仍旧。HTTPS 远端以控制账号绑定目录和仅本次生效的凭据 helper 执行：
   `GH_CONFIG_DIR=<角色固定目录> git -c credential.helper= -c 'credential.helper=!gh auth git-credential' -C <主工作树> fetch --no-tags <准确远端> refs/heads/<默认分支>`。
   这两个 `-c` 参数只为当前命令清空继承的 helper 并使用绑定账号的 `gh` 凭据，不修改全局或仓库 Git
   配置；仅设置 `GH_CONFIG_DIR` 不能证明 Git 已使用该账号。其他传输方式须按其实际认证方式核对身份，
   不能把 HTTPS helper 当作 SSH 身份切换。
   若现有 fetch 映射未覆盖该分支，在同一命令显式增加
   `--refmap=refs/heads/<默认分支>:<已核对远端跟踪引用>`；目标必须是该准确远端与分支对应的
   `refs/remotes/...` 引用，不固定写成 `origin/main`，也不使用空 `--refmap=` 跳过跟踪引用更新。
   随后立即以 `git -C <主工作树> rev-parse --verify FETCH_HEAD^{commit}` 取得完整提交 SHA，作为
   `<本次远端默认分支尖端>`；不能把 fetch 成功当成工作树已更新。后续命令使用该 SHA，不依赖可能被
   其他 fetch 改变的 `FETCH_HEAD`。准确来源与新鲜度适用时，后续清理可以复用这次抓取结果。
3. HEAD 与该 SHA 相同则无需更新。HEAD 是其祖先时，在准确主工作树执行
   `git -C <主工作树> merge --ff-only --no-autostash --no-overwrite-ignore <本次远端默认分支尖端>`。
   未提交内容不一概阻止同步：Git 能安全保留且不会覆盖原有现场时可快进，发生覆盖冲突或命令拒绝则
   停止同步并保留现场；不执行 reset、rebase、stash、clean、强制切换或创建合并提交来完成同步。
   若本地分支仅领先，报告“已包含远端最新提交，但存在本地额外提交”；若分叉，报告分叉。
   两者都不改写本地提交，也不将本地领先描述为与远端完全同步。
4. 更新后核对 HEAD、已核对的远端跟踪引用与记录 SHA、实际检出分支以及原有未提交内容的保留情况。
   记录本次同步到的提交；远端后来新增提交不影响这次按已抓取版本形成的结论，下一次合并或恢复再按真实状态处理。
   同步完成后，由主会话按规范第四节主动确认本轮需要使用的主工作树索引，按需刷新并将结果或缺口
   纳入现有收尾报告；不能把源码同步成功当成索引已更新，不要求每次同步全量初始化。

同步失败在现有进度和报告中保留具体原因及待完成动作，不声称本地收尾完成，不新建同步账本。
它不取消远端合并事实，也不新增对后续所有已批准任务的统一阻断；各任务仍依据实际依赖与原有授权
推进。下面的任务清理安全门与关闭限制独立适用，不得因主工作树同步成功或失败而绕过。

### 清理本轮任务对象

对本轮为当前任务创建且
所有权明确的专用工作树、远端任务分支及对应本地任务分支执行以下强制收尾；工作树与本地分支必须删除，
不能静默遗留：

1. 以实现者返回的“是否由本轮创建”、准确绝对路径、准确本地任务分支和对应实现头为所有权起点。
   只有已记录为当前任务创建的专用对象才能进入清理；主工作树、用户预先存在的工作树、其他任务工作树
   或归属不明路径一律不删除。
2. 从已合并 PR 的头仓库和头引用取得准确远端及准确远端任务分支，不得假定它与本地任务分支同名。回读
   远端默认分支名称。所有下述 fetch、push 与 ls-remote 命令仍须内联角色固定 `GH_CONFIG_DIR`。
3. 使用不依赖 `remote.<name>.fetch` 隐含 refmap 的准确来源引用执行
   `GH_CONFIG_DIR=<角色固定目录> git fetch --no-tags --refmap= <远端> refs/heads/<默认分支>`，随后立即以
   `git rev-parse --verify FETCH_HEAD^{commit}` 取得并记录不可变的 `<新鲜默认分支尖端>`，作为本次核对
   使用的最新远端默认分支。不得把 `FETCH_HEAD` 冒充远端跟踪引用，也不得在记录完整提交 SHA 前执行
   下一次 fetch。
4. 执行 `git rev-parse --verify refs/heads/<准确本地任务分支>^{commit}`，记录 `<本地任务分支尖端>`。
   随后执行
   `GH_CONFIG_DIR=<角色固定目录> git fetch --no-tags --refmap= <远端> refs/heads/<准确远端任务分支>`，并
   立即以 `git rev-parse --verify FETCH_HEAD^{commit}` 记录 `<首次远端任务分支尖端>`。任一引用不存在、
   不能解析为提交或 fetch 失败时停止。
5. 按以下顺序执行三项祖先检查：
   `git merge-base --is-ancestor <准确实现头> <新鲜默认分支尖端>`
   `git merge-base --is-ancestor <本地任务分支尖端> <新鲜默认分支尖端>`
   `git merge-base --is-ancestor <首次远端任务分支尖端> <新鲜默认分支尖端>`
   三条都成功才证明准确实现头、本地任务分支尖端与远端任务分支尖端均被这次准确抓取的新鲜默认分支
   包含；仅有 PR 页面已合并不足以替代任何一项证明。
6. 先按上文完成证据归档与产物清理，包括未被 Git 忽略的本轮证据；归档不能用于移走未提交源码以
   制造干净状态。仍有唯一必要证据、交付物或不明内容时，不删除整个工作树。
   执行 `git worktree list --porcelain`，确认准确绝对路径仍映射到准确本地任务分支，是与实现者返回事实
   相同登记工作树，并且该登记项没有 `locked` 标记。在准确工作树根执行
   `git status --porcelain=v1 --untracked-files=all`；输出必须为空，即不存在未提交的 tracked 或非忽略
   untracked 内容。
7. 在准确工作树根执行 `git ls-files --others --ignored --exclude-standard`，完整逐文件枚举 ignored 内容，
   不得使用会折叠 ignored 目录的状态输出。
   逐行确认每个文件都明确属于本任务且已可删除的构建产物、模型副本、缓存或已验证归档的源副本；
   任何其他内容、无法完整枚举或归属不明项都阻塞整个工作树的删除，不能以“存在证据”为由省略提取
   和其他可独立执行的产物清理；备份盘不可用时仍按上文暂停并等待用户裁决。关闭或结束所有仍使用该准确路径的角色、
   命令和会话，确认没有目录占用，同时确认没有活动 Git 操作、Git 锁或工作树锁。
8. 进入删除序列前再次执行
   `GH_CONFIG_DIR=<角色固定目录> git fetch --no-tags --refmap= <远端> refs/heads/<准确远端任务分支>`，并
   立即以 `git rev-parse --verify FETCH_HEAD^{commit}` 记录 `<删除前远端任务分支尖端>`。
   若两个远端任务分支尖端不同，或第二次 fetch 失败，立即停止，不删除任何引用、工作树或本地分支。
9. 在远端跟踪引用仍可解析时，先执行
   `git rev-parse --symbolic-full-name <准确本地任务分支>@{upstream}`，记录
   `<本地任务分支上游引用>`；它必须是准确远端与准确任务分支对应的远端跟踪引用，不得是默认分支、
   主工作树分支或用户分支。再执行
   `git rev-parse --verify <准确本地任务分支>@{upstream}^{commit}`，记录
   `<本地任务分支上游尖端>`，并执行
   `git merge-base --is-ancestor <本地任务分支尖端> <本地任务分支上游尖端>`。只有命令成功，才证明
   普通 `git branch -d` 仍具有安全合并依据；引用缺失、对象不符或祖先检查失败时立即停止，不得移动
   默认分支、主工作树分支、用户分支或任何其他引用。
10. 若没有 ignored 内容，使用 `git worktree remove <准确绝对路径>`；若普通状态为空且仅剩已逐项确认的
   ignored 内容，只允许对该准确绝对路径执行一次
   `git worktree remove --force <准确绝对路径>`。强制选项不得用于未提交内容、未合并提交、锁、占用或
   归属不明对象。命令中的路径必须是已核对的字面绝对路径，不得使用宽泛目录、未解析变量或通配符。
11. 工作树移除成功后只执行 `git branch -d <准确本地任务分支>`。若普通删除拒绝，停止清理并请用户
   裁决，不得升级强制分支删除。
12. 本地任务分支普通删除成功后，才允许执行唯一的条件删除命令：
    `GH_CONFIG_DIR=<角色固定目录> git push --force-with-lease=refs/heads/<准确远端任务分支>:<删除前远端任务分支尖端> <远端> :refs/heads/<准确远端任务分支>`。
    完整租约预期值必须是步骤 8 第二次复核得到的完整提交 OID，租约与删除 refspec 都必须使用准确完整
    `refs/heads/...` 引用。该窄化例外仅允许删除当前已合并 PR 的准确远端任务引用，
    不得创建、更新、回退或改写任何引用，其他强制推送仍禁止；不得使用 `+` refspec、其他强制选项或其他引用。
    若租约拒绝或命令失败，立即停止并报告，不得刷新预期提交后重试。
13. 远端条件删除成功后立即执行
    `GH_CONFIG_DIR=<角色固定目录> git ls-remote --exit-code --refs <远端> refs/heads/<准确远端任务分支>`。
    只有输出为空且退出码准确为 2 才证明远端任务分支引用已消失；仍返回引用或发生其他退出状态时停止
    清理并报告，不能把网络或认证失败当成引用不存在。
14. 删除后再次执行 `git worktree list --porcelain` 并检查准确路径与分支，确认工作树登记已消失、
   准确绝对路径已不存在、准确本地任务分支已不存在，同时回读主工作树状态，确认清理未影响其同步结果
   及原有未提交现场。

明确不得使用 `git branch -D`、不得使用 `rm -rf`、不得使用 `git clean`、不得使用
`git worktree unlock`，也不得用等价的宽泛或强制操作绕过安全门。任一安全门失败、删除命令拒绝或删除
后回读不满足全部后置条件时，停止工作树与分支删除并请用户裁决，保留准确证据；未触发备份盘不可用
的暂停要求时，上文独立核实的产物清理仍可执行，但不得用逐项删除掏空受保护的工作树来绕过安全门。
清理未完成时执行 Issue 不得关闭，
也不得推进下一个任务。清理完成后更新执行 Issue 的本轮任务进度；关闭及后续推进按下一节处理。

## 6. 交付推进与结束

按治理规范第六节“当前 Issue 推进与终止”核对验收与必要收尾。主会话更新执行 Issue 的任务、证据入口
和当前进度；仍有已批准且满足依赖的工作时，按该节回到第二节交接下一项任务。
需要组合审查时，向独立 `reviewer` 交付交付 Issue、适用子任务、相关 PR 和准确组合版本；将返回的组合
结论与证据按该节处理并记录。完成条件满足后由主会话关闭 Issue，更新适用上层摘要及指定 Project，报告并停止。
