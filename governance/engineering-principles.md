# 工程开发与审查准则

适用于实际工程开发、代码分析、实现、技术审查和重构；普通开发也适用，不要求启用开发 Skill。通用授权、异常处理、资源、记录与语言规则见[通用工作原则](common-principles.md)。本文件只维护工程设计和验证要求，不定义其他角色的内部工作，也不因被读取而启动工程闭环。

## 1. 行为约束必须有可追溯的依据

防止无依据约束、推测性保护，以及把实现事实当作需求。

- 先确认当前目标、硬约束、非目标和验收标准，区分已批准要求、已核实事实、待验证假设和建议。用户明确指定的实现边界属于硬约束；关键前提应能追溯到真实文档、代码、数据或运行环境。
- 每个新增或改变的硬约束都应说明适用来源及其如何导出具体限制。来源可以是当前已批准需求、正式合同、适用协议、架构决定或经核实的客观限制。提出者须指出现有能力的具体缺口，以及不增加该限制时哪项要求会在什么条件下无法满足；“更安全”或“以后可能需要”不能代替推导。代码、历史测试、工具默认值、惯例和代理推断只证明各自事实，不自动成为权威需求；建议写入计划或 Issue 也不因此取得批准。
- 按实际行为判断约束，不按名称或实现形式判断。下游不得擅自加强前置条件、缩小上游允许的合法输入域，或改变失败与资源承诺；超时、重试、批次、缓冲区、类型和默认值同样受此原则约束。
- 真实资源限制或故障证据不自动授权选择拒绝、丢弃或终止策略；这些行为仍须符合合同。无依据且非完成任务必需的机制不添加。历史行为暂未找到依据时，报告缺口并按当前授权处理，不自行删除或追认。

## 2. 领域语义和正式合同保持一致

防止局部术语、语义漂移、平行接口和影子合同。

- 同一业务概念在适用边界内保持一致的规范名称、语义和权威定义。沿生产者、转换边界与消费者核对正式定义；新增名称或接口须说明真实的概念或责任差异，不能用别名或包装重新定义同一事实。
- 优先复用正式接口、类型与数据模式。外部系统、版本或表示差异确需转换时，在对应边界完成必要映射，明确单位、时间含义、空值与未知、错误及状态等受影响语义如何保持一致；映射不得暗中增加业务判断、缩小合法输入域或成为第二合同。
- 必要的数据传输对象、包装层和序列化表示应有实际消费者或边界职责，并明确复用或转换哪些合同语义。语义一致不要求所有模块使用一个巨大模型，也不允许用不同名称掩盖同一合同的重复定义。

## 3. 状态和责任以完成合同所需的最小集合为准

防止重复字段、参数、业务判断和近似状态造成漂移与过度设计。

- 同一事实的权威归属、更新责任和冲突裁定必须明确。新增字段、参数、归属标记、副本或重复判断，须说明当前获批交付中的使用者、用途，以及为何不能直接使用或推导已有事实；用途可以来自本轮将实现的消费者、协议、持久兼容或恢复要求。仅为新增字段再增加读取者、校验或测试，不能证明整组机制必要。
- 必要缓存、只读投影、事务候选状态和快照应能说明实际用途、更新与失效条件及冲突处理，并保持产品合同；不从“权威明确”推导单写架构或物理单份数据。局部变化不因追求安全感而复制完整状态；需要完整候选时说明其原子更新或其他当前职责，以及局部增量为何不足。
- 简单性以必要的概念、状态、分支和维护责任衡量，代码行数只作辅助。不添加范围外功能、推测性扩展或单次使用不需要的抽象。单次使用且就近表达清晰的逻辑优先内联。提取函数或抽象应解决当前可说明的问题，例如明确独立职责、降低理解负担或复用已有逻辑；不为假想的未来复用增加层级，不拆出仅转发参数且无独立职责的辅助函数。
- 仅在承担明确错误处理责任的位置捕获错误，例如恢复、转换为边界约定的错误，或补充必要上下文；其他位置沿用既有错误传播机制。避免无处理作用的捕获、逐层重复记录后抛出，以及用默认成功结果掩盖失败。
- 优先复用成熟工具、库和协议实现。只有它们不能满足已确认需求，或引入成本、风险、许可及部署问题更高时，才说明缺口与取舍并考虑自研。技术方案明确复用部分与必要自研边界。

## 4. 验证必须针对明确失败条件并能识别相应错误

防止循环自证、无依据完整性机制和冗余提交后复核。

- 先明确待检验主张、适用合同或不变量以及失败判据，再寻找最可能推翻结论的反例与相反证据。对需求中的事实前提、方案、实现和审查意见使用同一标准；用户目标与授权边界始终遵守。
- 运行时校验、保护与完整性机制应对应真实故障模型，明确错误可能发生的时间、位置或责任边界，以及该错误如何使检查失败。对实现中的机制和拟提出的审查意见使用同一标准：先核对现有类型、事务、协议和存储保证，只针对未覆盖的失败增加必要机制，并遵守专项授权门。
- 外部输入在负责接收的边界完成必要校验。同一数据的同一条件已由边界校验、类型或既有机制保证，且该保证在后续流转中仍成立时，内部直接使用该保证，不逐层重复校验。确需再次校验时，说明哪个新边界或状态变化使原保证不再适用，以及尚未覆盖的失败条件。
- 自产数据及其自产摘要不能单独证明业务计算正确。核对业务计算错误时，摘要、逐对象 SHA、账户前后摘要或自证布尔是否仍会通过；若会通过，它们不能证明该业务主张。必要验证优先使用真实边界、可独立核对的小场景、明确期望或合同不变量，不以被测逻辑生成的期望循环自证，也不同时静默修改实现与期望。独立依据不要求复制完整算法或状态系统；同组件写入后读取的损坏检测可以有真实用途，不机械禁止摘要、断言或快照。
- 提交语义与结果已明确时使用已有保证；只有真实并发变化、结果不明或后续副作用等留下未覆盖的失败条件时，才针对缺口复核，并说明复核覆盖的时间窗口与最小数据范围。不同故障边界可检查同一事实，但不能成为冲突的语义裁决者；不无依据地完整重读、重算、重哈希或比较多份近似状态。
- 检查范围与任务风险、可逆性和规模相称。必要验证通过后，只有新变化、失败或未解决疑点才扩大或重复检查，不把审查变成穷举或新增需求。涉及不确定或易变化的第三方行为时，查询当前官方文档，必要时用实际环境、Issue、PR 或发布说明交叉核实。

### 验证结果与交付推进

防止把运行结束、记录失败或流程批准当作验收通过。普通开发与 GitHub 治理使用同一条件。

- 各交付动作以前置必要验证通过为条件。当前任务所需的测试或验收失败，或前置必要验证未完成、结果不明、证据不足时，停止受影响的提交、推送、请求交付批准、批准、合并和完成声明。按实际情况区分失败与尚未验证；如实记录问题、计划步骤做完、命令退出成功或正式审查批准，均不能代替合同要求在实际结果中成立。
- 失败后的证据保留、原因分析、联网查证、修复尝试及停止汇报，统一按[通用异常处理](common-principles.md#执行偏差与异常处理)执行。预期语义明确且修复属于当前授权时，可在该节停止条件以内排查、修复或调整普通实现方法，再验证受影响的要求；不重复申请已有授权。不得跳过失败继续依赖该结果的后续交付。
- 恢复交付须有适用于待交付版本、输入语义和环境的通过证据，并处理已发现的失败及其影响；已触发通用异常处理或专项规则的等待裁决条件时，还须取得用户的继续执行决定。旧版本通过、部分通过、取消、跳过或无结果不能替代尚缺的必要验证。复用仍适用的证据，只补修复及其影响所需的验证。不得为了继续流程擅自降低验收、删除有效失败测试、缩小任务或把未完成要求移出当前合同；测试本身偏离明确合同的，核实后按原合同纠正并重新验证。
- 验证顺序按任务合同确定。确需在提交或推送后运行的检查，须已明确对应阶段及所需动作；仅在前置必要验证通过且没有已知未解决失败时执行这些动作，后置检查通过前不得请求交付批准、批准或合并。不能事后以“运行 CI”“调试”或“保存现场”为由绕过已知失败。
- 工程验收按已批准实现合同判断，已有合同要求的真实输入验证或组合验收仍须完成。工程通过不证明来源研究结论或业务目标成立；合同明确要求记录实验结果时，按通用原则区分有效负面结果与实现故障。辅助工具故障按已有职责和替代证据处理，不能借此豁免必要验证。

### 代码检索与派生索引

防止查询错工作树、把不完整索引当成实现事实，以及为工具另建合同或任务状态。

- 查询定义、调用关系、消费者和影响范围时，优先使用可用且适用于当前工作树的 `codebase-memory-mcp`；字面量、文档和精确文本搜索继续使用 `rg`。未启用治理的任务可直接使用工具，不因此启用 GitHub 治理。
- 首次使用通过 `list_projects` 定位实际任务工作树，明确指定对应 `project`；创建或切换工作树后重新选择，不能沿用主工作树的项目名。用 `index_status` 核对根目录与索引状态；其中 `git.head_sha` 是查询时的 Git HEAD，不是索引生成版本，ready、路径或 HEAD 匹配均不能单独证明索引已覆盖当前源码。
- 对依赖图查询的相关文件或范围，用 `check_index_coverage` 核对文件新鲜度、覆盖信息与解析缺口，并处理查询分页；检查范围包含本轮有关的新增、修改和删除路径。新鲜度信号是尽力检测，未命中、无解析告警或部分结果均不能证明没有调用者或已经穷尽；关键结论回读当前源码，并按任务需要用测试验证。索引缺失、过期或覆盖不足时用源码检索补足，不把工具可用性变成额外审批门。
- 索引是可由源码重建的派生缓存，不代替需求、合同、批准状态、项目决策或验收。不开启 `manage_adr` 等功能复制 GitHub Issue、Project 或决策台账；随代码维护的技术文档仍按原有权威归属解释。
- 索引准备和刷新按实际查询需要进行，不要求每个任务或每次恢复全量初始化。安装、客户端配置和仓库内索引导出须有相应授权；只读任务使用工具前应确认初始化、查询和后台维护不会改动被审对象，不能保证时使用源码检索。治理中的角色职责与仓库外缓存边界由治理规范第四节统一规定。

## 5. 授权、不确定性与方案冲突

工程改动遵守通用工作原则中的[执行偏差与异常处理](common-principles.md#执行偏差与异常处理)、[新增校验与行为约束专项授权门](common-principles.md#新增校验与行为约束专项授权门)和[不确定性与方案冲突决策门](common-principles.md#不确定性与方案冲突决策门)。本节不另设审批或重试条件。

## 6. 最小修改与目标驱动执行

防止范围扩张、顺手重构与没有依据的完成声明。

- 每项改动应能追溯到当前请求；匹配现有风格，不顺手调整相邻逻辑或清理历史死代码。移除由本次改动产生的孤立代码，其他清理由用户明确授权。
- 先确定可验证目标，再实施并按第四节自审。修复代码缺陷时用能复现偏离的测试验证；重构核对原合同保持成立。验证方式服务于当前任务，不要求为规则文档建立测试。
- 简单、短时任务直接处理并做最小必要核对；复杂或长时工作按实际交付拆分，步骤写明动作与验证方式，不强制固定层级。可独立实施、跟踪或验收的工作可以成为任务；步骤保留在对应任务正文。需要组合验收的交付按第七节独立审查。

执行位置、计算配置、规则维护及证据归档与清理，分别按通用工作原则的[资源要求](common-principles.md#执行位置与计算资源)、[规则维护](common-principles.md#规则维护与上下文精简)和[产物生命周期](common-principles.md#构建产物与证据生命周期)执行。

## 7. 主代理编排与独立审查

防止职责混同、接受自述代替证据，以及执行与审查使用不同标准。

- 主代理维护适用任务事实源、决策、状态和最终验收。除交付的独立审查外，只把独立、有界、可验证且并行确有收益的任务交给子代理；同一共享写入路径只有一个写入者。
- 实现者在选择机制和创建提交前按前四项工程原则自审本轮有意义的差异；新增约束、语义、状态或证明机制的提出者说明适用要求、现有能力的具体缺口及最小必要实现，任务整体必要不能代替其中机制必要。审查者用同一方法独立核对真实请求、实际消费者、已有保证和反例；描述工作方式、存在消费者或测试通过均不能单独证明必要性。必要依据留在已有方案说明、交接、PR 或 Review 的对应位置，不逐字段制作固定表单或另建账本。
- 当前改动已确认违反适用需求、正式技术合同或工程治理规则，必须阻塞；必要验证失败或不足以证明验收成立时，按第四节停止交付推进，须指向具体位置、失败或证据缺口。发现实现已加入未授权行为与要求增加新行为分开判断；审查者的偏好、假想风险或合同外要求不能自动成为阻塞。
- 主代理回读子代理结果和真实证据，对批准与返工结论均核验依据并分流；不以结论标签代替证据，也不重复完成一轮完整审查。
- 需要组合验收的交付，在宣布完成前派出独立子代理做只读、全面的对抗性审查，核对准确组合版本和整体行为；有可执行问题则按通用异常处理组织范围内修复与再次审查，达到异常处理停止条件时交用户决定，不能以“修复到通过”为由继续试错。各任务分别完成不能代替组合验收。
- 各角色和独立审查使用当前角色已配置的模型与推理等级，不统一强制推理等级或另作任务级覆盖。审查通过不自动授予提交、推送、PR 或合并权限，交付动作按用户授权与目标仓库规则执行。

### 提交前独立内容审查

防止实质设计问题只在首次提交后的 PR 审查中被发现。未启用治理的任务同样适用，不因此启用 GitHub 治理。

- 本轮新增或改变运行时接受、拒绝条件，领域合同及跨边界转换语义，同一业务事实的可变副本或权威关系，或运行时放行、验收所依赖的证明与复核机制时，主代理在创建对应提交前安排独立只读内容审查。按实际行为判断，不按 SHA、DTO、快照等名称或“重构”标签触发；未涉及这些变化的局部变量、格式与机械整理沿用原有审查方式。仅补充验证既有要求的普通测试，且未改变验收含义或运行时状态、放行条件时，不自动触发此项额外审查；测试若改变这些含义或引入影子证明机制，仍按实际行为判断。
- 实现者完成前置必要验证与自审后交付准确候选；候选用现有 Git 基线、完整待提交差异及相关源码界定，覆盖新增与删除文件，区分暂存区与工作区。审查期间不并发改写候选；发现问题先按当前授权修正并重新验证，受影响内容通过后才提交。既有提交不重写历史，核实其差异和未解决问题，再按当前条件审查与修复；不能因已经提交就绕过后续交付门。
- 提交前结论仅说明所审内容及前置验证，不是正式 PR 批准，也不放行尚未完成的后置检查。提交内容、基线或相关条件变化时补审受影响部分；提交后复用仍适用的内容证据，核对准确版本、候选一致性、新变化及后置检查，不重复完整审查。治理中的角色交接与正式 Review 遵守治理规范第六节，不新增候选哈希系统、批准布尔或预审状态文件。

## 8. GitHub 任务治理

工程 Skill 的启用、角色编排与交付条件由[治理规范](codex-development-governance.md)维护；工程对外接单和返回遵守[交接协议](group-collaboration.md)。未启用开发流程的工程活动只遵守适用工程原则，不因此创建 Issue、PR 或派生开发角色。Issue 呈现与维护使用[通用记录要求](common-principles.md#issue-呈现与维护)。

### 工程裁决与执行记录

防止执行授权和流程状态被当作工程裁决，污染后续合同回顾。

- 项目裁决索引只收录影响项目目标、业务语义、架构、接口、数据语义、实质验收或工程取舍的决定，
  包括改变实际资源、部署或资金承诺的边界；是否收录取决于决定的实质内容，不取决于是否经过用户批准。
- 单纯开工、暂停／恢复、Agent 交接、阶段签发、审查合并、任务管理和操作回执留在所属任务 Issue 或 PR，
  按职责更新现有进度、父级摘要及 Project，不进入项目裁决索引，也不为这些状态建立裁决编号或替代关系。
- 普通实验结论与运行回执留在所属研究任务；研究发现被采纳并实质改变上述工程边界时，由获授权的工程流程维护原有裁决入口，工程记录引用原始研究证据。
- 同一消息兼有工程决定与执行指令时，索引只收录工程变化并引用原始决定；既有工程语义的重述、确认或
  继续执行不新建裁决。授权和执行依据仍保留在所属任务，不因不进入索引而省略或失效。
