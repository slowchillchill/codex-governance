# Codex 原生 GitHub 交付治理规范

版本：`0.7.0`

状态：`SUPERVISED_TRIAL`

## 一、目标与非目标

本规范在用户显式调用治理 Skill 后，让一个 Codex 主会话担任 `orchestrator`，并使用 Codex 原生自定义
子代理完成用户明确签发的一个任务或父交付，包括建立或定位准确 Issue、规划、实现、独立审查、
返工、合并和收尾。

项目总体规划与展示可使用明确指定的 GitHub Project，任务合同保存在 Issue。它不替换或修改其他治理
工具，不强制配置看板，也不建设新的工作流引擎、状态机、授权账本、后台守护进程或轮询器。

本规范不使用 `/goal`。一次运行的终点是本轮交付完成、出现必须由用户裁决的情况，或用户主动停止。
进程退出后的恢复依赖 GitHub 持久事实与本地 Git 实现事实，而不依赖会话持续存在。

## 二、启用条件与当前请求边界

只有同时满足以下条件才启用本治理：

1. 目标仓库根 `AGENTS.md` 明确声明采用本规范；
2. 用户在当前消息中显式调用 `codex-stage-orchestrator`，并给出一个明确开发需求；准确 Issue URL
   或编号可以提供，但不是必填；
3. 主会话能从当前工作目录唯一确定目标 GitHub 仓库。

启用后由 `orchestrator` 定位或创建与本次需求一致的准确交付 Issue；确定该 Issue 后才派生
下游角色。

显式调用是指 `$codex-stage-orchestrator` 或明确要求“使用 codex-stage-orchestrator”。未显式调用时不启用
本治理；用户明确禁止使用时不启用。仅提及名称、询问或修改 Skill、历史调用、仓库接入声明、任务大小
或启动 `--profile codex-governance` 均不能替代显式调用。

身份核验和 Issue 查询之前先判断启用条件；未启用时按用户授权处理普通任务，不因本治理创建 Issue、
派生治理角色或执行 GitHub 闭环。同一已显式授权任务内的澄清、状态查询和继续执行沿用该任务授权；
本轮批准范围以外的新任务或下一阶段必须重新显式调用。Skill 的 `agents/openai.yaml` 设置
`policy.allow_implicit_invocation: false`，关闭隐式调用。

仅讨论需求，或关键语义尚不足以确定准确任务时，主会话先在当前会话中按第六节的澄清方法核实和整理，
不因形成草稿提前创建 Issue。满足启用条件并确定准确 Issue 后，才把当前任务交给规划角色细化。

`orchestrator` 先只查询当前仓库的 GitHub 当前事实。用户给出 Issue 时核对其仓库、状态与当前合同；
未给出时，定向读取可能承载本次需求的现有 Issue；恰有一个当前合同能够完整承载本次需求时，将它
定位为唯一匹配对象。没有合适对象时，依据用户本次需求创建最小必要 Issue；正文遵守工程准则第八节的
呈现与维护要求，只纳入当前需求及已有授权支持的内容。出现多个候选、合同冲突或无法唯一判断时停止并
请用户决定，不创建重复 Issue。

Issue 定位不得跨仓库扫描，不得按最旧 Issue、最小编号、标题、标签、Milestone 或看板排序自动选择任务。
父 Issue 只有被本轮显式签发时，才允许按其合同选择已批准子任务；单独签发子 Issue 不授权兄弟任务或
父级关闭。规划未来工作可以记录在 Project 或适用合同中，须保留真实批准状态，不能直接派发实施。

交接始终区分本轮交付 Issue 与当前执行 Issue：普通任务时二者相同；显式签发父交付时，前者保存本轮
整体目标、已批准子任务范围和组合验收，后者承载当前实施任务。主会话可以顺序完成该范围内的子任务；
后来挂入的子 Issue 只有已属于本轮批准范围时才可执行，不能因关联或状态变化自动获得授权。
属于批准范围的必要拆分可以创建最小必要子 Issue；扩大目标、验收或交付承诺时，按第三节裁决。
跨仓库依赖只作为依赖引用，不自动成为本轮实施任务；保留目标仓库现有执行边界。

本轮交付完成后必须停止，不创建、选择、激活、批准或签发范围外任务。既有项目、模块、阶段 Issue
继续作为历史及当前合同依据；旧阶段正文中的已批准任务和步骤可以继续执行，不强制拆分、补建父级或
迁移，也不把旧父子关系自动解释为整棵任务树的授权。

## 三、事实来源与工程原则

1. 用户当前明确指令决定目标、授权和最终裁决。
2. 本轮交付 Issue 与当前执行 Issue 正文分别保存适用目标、范围、非目标、批准边界、任务、步骤和验收；
   普通任务不要求父级。父交付的子任务范围和组合验收不能被子任务或 PR 自行改变。
3. Project 保存项目目标与范围概述、规划入口和管理视图；长期架构、接口与数据语义由技术文档承载。
   已有正式总体合同直接引用，不复制。角色只按任务需要读取适用父合同、Project 概述和技术文档。
4. 真实源码、Git 工作树、分支、提交、远端引用、测试与运行结果证明实现事实。
5. PR 保存实现差异、测试证据、讨论与返工；GitHub Review 保存正式 PR 审查结论；合并提交保存结果。
   独立组合审查结论由主会话记录在对应交付 Issue。
6. 通用工程原则及 Issue 呈现与维护规则由 [工程准则](engineering-principles.md) 维护；
   本规范保存闭环权责，角色 TOML 保存角色入口，Skill 引导程序读取。它们不记录当前任务状态。

各角色在当前上下文未载入工程准则时，先读取上述文件，再按其前四节处理约束依据、领域语义与合同、
状态与责任、验证及真实失败条件。普通开发同样适用这些原则，不依赖本闭环启用。
源码、测试和运行结果不能自行改变批准合同；代理建议写入 Issue 也不因此取得授权。必要依据写入现有
范围说明、PR 或 Review，不建立额外的约束登记表、证明摘要或状态账本。

公开的 Issue、PR、Review、文档及附件使用仓库相对路径或通用参数说明，不粘贴本机绑定、工作站路径、
认证资料或包含这些内容的原始日志。验证结论保留实际结果和必要证据，发布前去除这些个人配置内容。
清理所需的准确工作树绝对路径仍在私有会话及角色交接中传递，不以公开的相对路径替代所有权依据。
GitHub 本身显示的作者和操作账号身份属于公开活动；隐藏运行绑定不等于隐藏平台上的操作身份。

GitHub 是唯一任务治理账本；本地 Git 状态是不可忽略的实现事实，但不是第二任务账本。不得创建本地
游标、状态 JSON、任务镜像正文或重复叙述任务过程的证据文档。按工程准则第六节保留的原始验证材料、
报告和必要复现输入属于交付证据，可以在仓库外归档；它们不保存另一份合同、批准状态或进度。
代码图只保存可重建的源码查询缓存，辅助定位定义、
消费者与影响范围；查询结果经源码核实后进入现有规划、PR 或 Review，不自动扩大 Issue 的批准范围，
不另建 ADR、Issue、Project 镜像或索引状态表。通用查询方法统一遵守工程准则第四节“代码检索与派生索引”。

Issue 的正文结构、技术折叠、完成语义、替换式更新及父子摘要遵守工程准则第八节“Issue 呈现与维护”。
各角色读取适用的完整合同，包含折叠技术内容；本仓库的角色入口与接入模板不另维护格式。
Issue 正文及正式合同续篇的效力、普通评论与技术文档的分工也以工程准则第八节为准。

不确定性、合同冲突与新增校验或行为约束按工程准则第五节处理。预期语义无争议且修复属于当前授权时，
纠正已证实的实现偏离；需要选择语义、改变合同或扩大授权时，停止受影响工作并请用户裁决。评论记录
裁决经过；裁决改变合同时，同步更新对应 Issue 正文或正文链接的合同续篇。

## 四、角色与身份

| 角色 | 本机身份绑定 | 职责 | 禁止事项 |
|---|---|---|---|
| 主会话 `orchestrator` | `github.controller` | 确定交付边界、维护合同与展示状态、分配已批准子任务、顺序派生角色、分流 Review、合并与收尾 | 不代替独立审查，不选择范围外任务 |
| `scope-planner` | `github.controller` | 只读澄清当前需求，返回验收场景、最小任务及必要依据 | 不修改被审对象、Issue、PR，不实施 |
| `implementer` | `github.implementer` | 创建任务分支与专用工作树，实施、测试、提交、普通推送并创建或更新 PR | 不扩大合同，不合并 |
| `reviewer` | `github.controller` | 只读审查待提交候选、当前 PR 精确头或交付组合；仅对 PR 提交正式 Review | 不修改被审对象，不合并 |

### 代码查询与索引职责

工具使用安排在现有角色步骤内，不增加角色、审批阶段或通用启动门禁。治理授权和本节身份核验通过后，
`orchestrator` 在确实需要代码探索时选择当前已有工作树，可按需准备仓库外索引缓存；交接实际工作目录、
适用源码版本和影响本轮判断的已知缺口，不为准备索引代替实现者创建任务工作树。`implementer` 在创建
或接手任务工作树后选择或建立该工作树的索引，并按修改和查询需要刷新；不能继续查询主工作树来代替
任务工作树。索引不可用时通过源码补足证据，不因此阻断原本可执行的任务。

在两个现有交接点主动确认本轮需要使用的索引：`implementer` 交付审查前确认任务工作树索引，
`orchestrator` 同步本地主工作树后确认主工作树索引。按工程准则第四节检查相关变更路径或范围；
已有适用的新鲜度证据时复用，缺失、过期或无法确认时，由对应维护角色在仓库外缓存边界内按需建立
或刷新，再核对相关范围。不假定后台监听覆盖被查询的每个工作树，也不以会话重连证明离线变化已补齐。
在现有交接或收尾报告中说明确认、刷新结果或具体缺口；失败或仍无法确认时使用当前源码核验，
不得宣称索引已更新。本轮不使用代码图时不创建索引，不要求固定全量重建；刷新成功不成为新的
Review、合并或关闭 Issue 门槛。

`scope-planner` 与 `reviewer` 可查询已有索引，关键结论回读源码。已配置工具在初始化、查询或后台维护
中产生的、经验证只位于仓库外且可由源码重建的内部缓存，可以自动更新；这不授权修改被审源码、
仓库文件、Git 引用或配置、合同、决策记录及客户端配置。两个只读角色不主动初始化、重建或删除索引，
也不在任务中安装、升级或重新配置工具。不能保证上述边界，或索引与被审版本不符且不能用现有证据
补足时，转用源码查询。

接入或调整工具时须核对初始化及后台维护的实际副作用，使用仓库外缓存，不启用仓库内索引导出。
不能仅凭查询命令、`persistence=false` 或干净的 `git status` 断言无仓库写入：已有仓库内索引产物可能
触发自动刷新，忽略文件及 Git 配置也可能变化。接入与验证方法集中在
[安装说明](../docs/installation.md)，本规范不复制工具配置。

### 本机配置与规则定位

账号与路径只在仓库外的私有 TOML 中维护，公开示例见
[本机绑定模板](../templates/local.example.toml)。代理通过工具读取它；它不是 Codex 原生配置层，也不是
认证文件或任务账本。配置定位顺序为非空的 `CODEX_GOVERNANCE_CONFIG`，否则使用
`${XDG_CONFIG_HOME:-$HOME/.config}/codex-governance/local.toml`。各入口保留这一最小定位说明。

| 字段 | 含义 |
|---|---|
| `paths.source_root` | 本机治理源仓库的绝对路径，用于定位工程准则、治理规范和 Skill |
| `evidence_archives[].git_common_dir` | 可选归档绑定对应仓库的 Git 公共目录实际绝对路径，用于准确匹配主工作树及其任务工作树 |
| `evidence_archives[].root` | 该仓库已授权的证据归档根目录绝对路径；不作为其他项目的默认目录 |
| `evidence_archives[].mount_point` | 归档盘应实际挂载的目录绝对路径；使用前核对挂载及目标文件系统 |
| `github.controller.login` | 主会话、规划及审查角色的预期 GitHub 登录名 |
| `github.controller.config_dir` | 控制账号的 GitHub CLI 配置目录绝对路径 |
| `github.implementer.login` | 实现角色的预期 GitHub 登录名 |
| `github.implementer.config_dir` | 实现账号的 GitHub CLI 配置目录绝对路径 |

路径是普通 TOML 字符串，填写实际绝对路径，不对值执行 shell 求值，不假定 `~` 或 `$HOME` 会自动展开。
模型、推理等级和命令权限由该入口的 Codex 原生配置、可选 Profile 与角色 TOML 维护，不在这里重复定义。
本机绑定只保存非认证元数据；不读取、复制或公开其指向目录中的认证材料。

`evidence_archives` 是可选的 TOML 表数组，按仓库分别配置上述三个字段，不保存任务状态。
使用归档时，以当前工作树 `git rev-parse --path-format=absolute --git-common-dir` 的结果解析实际路径，
与 `git_common_dir` 唯一匹配；不按目录名、项目简称或路径前缀猜测。`root` 的实际路径须位于所配置的
已挂载 `mount_point` 内，且不能位于待清理工作树或构建输出内。匹配缺失或重复时，保留待迁移证据并
报告缺口，不借用其他仓库的绑定。备份盘不可用时，按工程准则第六节立即停止当前任务并向用户汇报，
等待裁决；下游角色立即停止并返回主会话，由主会话向用户汇报，不自行批准继续。仅在需要归档时检查
这些字段，不把备份盘可用性设为所有任务的启动条件。

普通任务在需要读取工程准则时，只读取 `paths.source_root` 并定位其下的
`governance/engineering-principles.md`；这不启用治理，也不触发身份核验或 Issue 查询。
普通任务执行已授权的证据归档时，可以额外读取当前仓库的 `evidence_archives` 绑定，同样不启用治理。
使用本地来源直接读取本文的角色按第三节读取工程准则。配置或规则来源无法读取时，按工程准则第五节
处理事实缺口，不猜测作者路径或回退到其他账号。

### 身份核验与命令归属

三个治理角色可注册在普通启动配置中，但只接收用户显式启用后由父级 `orchestrator` 交付的任务。
角色先依据交接上下文确认这一授权；缺少时直接返回缺口，不读取身份绑定、不核验身份或执行治理操作。
同一已授权交付的后续交接沿用原授权，不要求用户在每条子代理消息中重复调用。

确认治理启用后，各角色先只读取得本机配置及上表中的本角色绑定，随后立即使用该绑定
的 `config_dir` 内联执行 `gh api user --jq .login`，将结果与同一绑定的 `login` 核对。该只读配置步骤
仅用于解析原有身份核验的参数；除解析绑定所必需的本地操作外，核验通过前不开展其他任务工作。

命令形式为 `GH_CONFIG_DIR=<本角色绑定目录> gh api user --jq .login`；执行时用实际路径，并按 shell
规则正确引用空格等字符。不得把继承环境中的 `GH_CONFIG_DIR` 当成身份事实；继承目录错误时，绑定目录
自动覆盖它。所需绑定缺失、目录不可用或实际登录名不符时，停止相关治理工作并报告缺口；其中
`implementer` 必须在任何代码修改、实施测试或 GitHub 写入前停止。

核对通过后，每一条需要 GitHub 认证的 `gh` 或远端 `git` 命令仍须内联该角色的绑定目录，不回退到
继承环境。不得执行 `gh auth switch` 或修改全局活动账号，也不得读取、复制认证材料。
公共配置示例不再另外设置 `shell_environment_policy.set.GH_CONFIG_DIR`；本机绑定是唯一账号与目录来源。

角色约束属于受监督职责分离，不等同于操作系统级或凭据级强隔离。目标仓库明确接入本治理后，角色
独立性本身构成顺序派生理由；仍然一次只推进一个角色，同一写入路径只有一个 `implementer`。
首次交接使用 `scope-planner -> implementer -> reviewer`；需要提交前内容审查时，由主会话在同一
实现者与审查者之间顺序交接修复、提交及正式 Review，不增加角色，也不让审查者代为修改或提交。

普通启动沿用该入口已有的主会话模型与权限，Skill 不切换 Profile、模型、命令权限或并发设置。
可选 Profile 和三个角色的示例默认使用 `danger-full-access` 与 `never`，提供等价 YOLO 的命令执行权限。
OpenAI 当前行为还会在派生子代理时重新应用父会话的实时权限覆盖。默认
权限或实时覆盖都只改变命令执行权限，不扩大角色职责、GitHub 身份、本轮批准范围或破坏性操作授权，
也不解除管理员绕过禁令。即使命令技术上可写，`scope-planner` 与 `reviewer` 仍须保持被审对象只读。

## 五、启动与恢复

`orchestrator` 在任何写操作前先依据第二节定向查询当前仓库 Issue；只有确定没有合适对象时，才创建
最小必要 Issue。准确 Issue 确定后同时回读：

- GitHub：本轮交付 Issue、当前执行 Issue、适用父合同、相关 PR、完整 Review、检查与审查线程；
  签发父交付时，核对已批准子任务及原生关系；配置 Project 时读取必要的项目引用与实际条目；
- 本地：`git worktree list --porcelain`、相关工作树 `git status --short --branch`、分支、远端跟踪与
  ahead/behind 状态。

需要父子关系时，通过 GitHub REST `GET /repos/{owner}/{repo}/issues/{issue_number}/parent` 和
`GET /repos/{owner}/{repo}/issues/{issue_number}/sub_issues` 读取实际对象，按需向上读取适用合同，
不依赖标题或正文链接猜测原生关系，也不为普通任务虚构父级。关系与合同批准范围分开核对；关系、正文
指针、批准状态或当前任务冲突且无法按既有授权消解时，交给用户裁决。旧阶段按其现行合同和证据恢复。

恢复时按真实状态继续，不重复创建对象。先恢复适用验证及未解决失败的事实，再按第六节决定能否推进；
已有提交、PR 或正式批准不能绕过[工程准则的“验证结果与交付推进”](engineering-principles.md#验证结果与交付推进)。

| 已存在状态 | 恢复动作 |
|---|---|
| 工作树有未提交内容 | 保留现场，确认属于当前任务后交回同一 `implementer` |
| 本地分支领先远端 | 回读差异、Issue 与验证证据，满足第六节实现交付条件后才普通推送，否则保留现场并分流 |
| 远端分支存在但没有 PR | 先查同头分支 PR，再决定是否创建 |
| PR 已存在 | 从当前 PR 头、Review、检查与线程继续 |
| Review 已提交 | 以 GitHub 正式 Review 为准，不依赖子代理消息 |
| PR 已合并但收尾未完成 | 回读合并事实、本地主分支及任务树状态，按第六节幂等补齐同步和必要清理，再维护 Issue |
| 子任务已关闭但父交付未完成 | 核对关闭原因与验收证据，继续已批准范围或组合审查，不按关闭数量认定成功 |
| Project 与 Issue 状态不一致 | 以 Issue 和审查事实补充展示更新，不改变合同或重新开启实施 |
| GitHub 写操作超时 | 先读取远端实际结果，不盲目重复写 |

已有提交前内容审查时，核对其基线、完整候选差异及适用验证是否仍对应当前待提交内容；缺少依据或
存在新变化时按第六节补审。既有提交不为补前置审查而重写历史，也不能用既有提交或批准绕过当前检查。

存在无法确认归属的未提交内容、当前 Issue 的第二个活动编排者，或其他治理工具正在治理同一 Issue 时，保留
现场并请用户决定。

### Project 接入与状态维护

目标仓库可声明 `项目看板：<Project URL>`，或由用户明确指定本轮采用的 Project；未配置时继续 Issue
闭环。只关联和维护明确指定的 Project，不遍历用户或组织看板来猜测目标；指定含义不明时报告展示配置
缺口。创建 Project、修改字段结构和批量导入属于另行明确提出的项目管理工作，不附带在普通任务中执行。

主会话使用现有 CLI/API 读取 Project、条目、字段及选项的实际标识，复用原生负责人、标签与父子关系，
不增加本地映射表或配置系统。接入建议见[安装说明](../docs/installation.md#7-project-接入建议)；既有
Project 不强制改名或重建字段，使用已有明确对应选项，缺少合适选项时报告缺口。

在开始工作、进入审查、阻塞或暂停、恢复、结束等有意义的变化后，主会话维护相关条目的实际状态。
“已结束”只依据 Issue 关闭事实，成功、取消和重复按关闭原因解释；不得通过拖动卡片绕过验收与关闭门。
合同和必要依据完整时，权限、字段或网络等导致的 Project 更新失败不阻塞已授权任务；在现有 Issue
进度和交付报告中说明未同步内容，不宣称更新成功，也不创建同步账本。写入结果不明先查询实际对象，
再补充未完成操作；恢复时依真实状态更新。若缺失内容决定任务范围，仍按事实缺口规则暂停受影响工作。

## 六、当前 Issue 闭环

`orchestrator` 负责本闭环的进度维护，按第三节引用的工程准则在角色交接、阻塞、暂停／恢复和完成时
核对并更新执行 Issue、适用的父交付摘要及已指定 Project；下游角色交付本轮成果及剩余缺口。
父正文记录当前子任务及下一项已批准交付，具体步骤留在子任务正文。显示代码已合并或正在收尾，不代表任务已完成，
推进和关闭仍须满足本节的验收与清理要求。

### 1. 范围规划

`orchestrator` 向各角色交付准确的本轮交付 Issue、当前执行 Issue、适用合同、相关项目决策引用、必要
Project 引用和工作目录。决策入口沿用用户指定、目标项目声明及当前合同中的已有引用，传递准确仓库的
完整 Issue、评论或索引链接；不同项目分别定位，不固定公共 Issue 编号，也不要求新建集中决策 Issue。
引用不足时，主会话按本轮任务涉及的主题在当前项目定向补查，不默认扫描全部历史；只有仍缺少影响判断的
关键决定时才返回具体缺口。跨仓库决定须被当前项目明确采用才适用。各角色沿用相关引用，按需读取原文，
不另建决策台账；未声明入口不代表已有决定失效，也不单独构成阻塞。
`scope-planner` 只读核对适用
`AGENTS.md`、合同、实际消费者、源码、测试和 Git 状态，把当前需求整理成可实施、可验收的最小范围，
防止模糊要求被补成新需求、任务遗漏或方案先于需求。需要结构探索时按第四节查询已有代码图，
核实真实定义、消费者及跨模块关系；索引不能代替源码与适用合同。

先提取目标、行为、明确约束与非目标，再查已有合同能够回答哪些问题。只对仍会影响业务语义、范围或
验收的缺口提出具体问题，说明已知依据、缺少的决定和不同答案的影响，交主会话向用户澄清。不设固定
提问数量，不用行业惯例补齐未获批准的业务要求；保持已批准语义的普通实现选择自主处理。

规划结果按任务需要包含：

- 要实现的行为与最小修改范围，明确非目标；容易歧义的要求用初始条件、动作、预期结果和失败表现
  表达验收。性能、容量、时间等数值须有正式依据或用户决定，不能为填满验收内容而编造指标；
- 拟复用的正式合同、规范术语、权威状态和实际边界，以及新增限制、接口或状态的必要依据。长期定义
  引用其权威位置，避免复制成局部合同；
- 服务于这些要求的最小任务、真实依赖与必要验证，指出最可能推翻方案的反例。按用户目标、价值与
  依赖提出顺序；已有批准顺序继续遵守。按工程准则区分可独立跟踪的任务和正文步骤，不强制拆分旧阶段；
  基础设施任务按实际技术依赖组织，不强求每项任务都是可独立部署的用户功能；
- 尚未解决的决策缺口、合同冲突及其影响的工作。

规划时核对“已批准要求 → 必要任务 → 验收方式”，反向检查任务及其中有意义的新增机制是否有必要
依据，按工程准则前四节说明现有合同、接口、状态或工具留下的具体缺口；不能从任务整体必要直接推导
其中每种机制必要，也不能把建议、计划步骤或自产测试作为依据终点。核对术语与正式接口的一致性。
关系用现有条目和引用说明，复杂时才使用表格；正文按第三节引用的
工程准则中的呈现规则组织，不要求逐行代码编号、空栏目或额外追踪清单。简单任务可用简短范围说明完成这些判断，
角色职责与启用条件不变。

`scope-planner` 可以返回可直接合入 Issue 的建议文本，但不修改被审对象或 Issue，也不批准自己的建议；
工具自动缓存更新只按第四节的窄化边界处理。
`orchestrator` 只把已有授权支持的必要结论写回当前 Issue；缺少授权的建议不混入可执行任务。
实质改变范围、验收、已批准方案、批准状态或游标时，先按第三节取得用户决定，再替换受影响的当前合同，
不因澄清措辞或普通实现选择重复申请批准。

### 2. 实现

`implementer` 从最新默认分支建立 `issue-<Issue编号>-<任务-slug>` 分支；需要隔离时创建任务专用
工作树。它只实施当前任务的已批准范围，按任务性质验证并自审差异。触发工程准则第七节
[提交前独立内容审查](engineering-principles.md#提交前独立内容审查)时，先返回准确候选交主会话安排
第三小节的内容审查，不能先提交或推送；未触发时沿用提交后的独立 PR 审查。提交、推送的前置必要
验证及适用内容审查通过，且没有已知未解决失败时，才创建提交、普通推送。验证失败或证据缺口按第四小节分流，先修复或报告，
不能仅将失败写入 PR 后继续交付。验证顺序和恢复条件统一遵守
[工程准则的“验证结果与交付推进”](engineering-principles.md#验证结果与交付推进)。
需要代码图时，按第四节选择或建立此任务工作树的索引，修改后按实际查询需要确认新鲜度，并在交付
审查前完成该节规定的新鲜度确认与必要刷新；自审中的影响范围查询继续核对当前源码。
实施前核对分配任务与当前要求、依赖和验收的对应关系；发现关键缺口时返回主会话，按第四小节分流。
选择机制及提交前自审时，从要求检查实际实现和证据，再按工程准则前四节反查新增约束的授权推导、
定义与消费者、状态用途及已有保证的具体缺口。必要解释留在现有交接和 PR 的对应位置，不逐字段填表。
已确认的本轮偏离先修正；不能用“测试已通过”代替机制必要性检查。

`implementer` 按工程准则第六节“构建产物与证据生命周期”管理开发期间的占用，交付审查前独立保存
必要证据；具体归档与产物清理方法见编排程序第五节“证据归档与产物清理”。在现有交接中提供证据入口、
准确产物路径与归属、仍需保留对象及原因，实际本机路径仅在私有交接中传递。`reviewer` 只读核对证据
是否足以支撑当前结论、是否仍依赖将被删除的临时文件，不执行迁移或清理。`orchestrator` 负责合并后
核验归档与清理结果；同一路径仍只有一个执行写入的角色，交接后再执行收尾。

`implementer` 返回结果时还必须明确专用工作树是否由本轮为当前任务创建、准确绝对路径、准确本地任务
分支及对应实现头。后续清理只能依据这些已记录事实与 Git 当前事实确认所有权，不得按分支名称或目录
前缀猜测。

PR 关联实际执行的 Issue，普通任务（包括独立执行的子任务）的中间 PR 使用 `Refs #<Issue编号>`。
只有最终 PR 覆盖执行 Issue 的剩余要求与适用组合验收，
且未创建专用工作树、无需合并后清理时，才可使用 `Closes #<Issue编号>`；其他普通任务 PR 使用 `Refs`，
完成全部任务、验收与必要清理后由 `orchestrator` 手动关闭 Issue。
父交付及需要合并后独立组合审查的旧阶段仅使用 `Refs`，不得使用 `Closes`。关闭一个子任务不代表关闭父交付。
PR 正文保存当前任务、修改摘要、要求与实际实现及验收证据的对应关系、实际验证结果和剩余问题。
对应关系沿用规划中的任务条目或合同引用，不复制完整任务正文。`implementer` 不合并 PR，
也不创建下游任务。

### 3. 独立审查与正式 Review

触发提交前内容审查时，主会话向同一 `reviewer` 交付准确 Issue、本轮分配范围、实际 Git 比较基线、
完整待提交差异、相关源码及前置验证证据。候选和触发范围遵守工程准则第七节；须区分暂存区与工作区，
覆盖新增、修改和删除文件，确认验证对应所审候选，不能用只含部分文件的差异遗漏本轮行为变化。
审查者只读返回所审基线与候选、结论、发现及证据，由主会话按第四小节分流；此时不要求 PR 已存在，
不创建 PR 或提交 GitHub Review。候选审查期间实现者停止写入；返工交回同一实现者修正和验证，再审
受影响部分，通过后才提交、推送和维护 PR。内容结论不代表后置检查已通过，也不代替正式批准。

两种审查使用同一标准。`reviewer` 读取准确 Issue、候选或 PR 当前头、完整差异、对应测试结果及已有
检查和线程，先提出足以推翻“可以通过”的失败条件，再按第三节所引用的工程原则检查差异及真实消费者，以证据判断。需要
代码图时按第四节查询与被审版本相符的已有索引，寻找消费者和反例；索引不符或不可用时直接读源码。
审查范围以 Issue 中分配给本轮的任务及主会话交付范围为准；PR 正文不能自行缩小任务，也不要求单个
PR 提前完成交付范围中尚未分配的其他任务。

双向核对要求、实现与证据：检查本轮已批准要求是否落实到真实行为和必要验证，识别遗漏、部分实现及
偏离；反向追查新增行为、接口、状态和限制的依据，识别无依据新增内容。检查重点是有意义的行为与
设计变化，不要求逐行代码建立需求映射。不能仅因规格、计划、代码彼此一致就认定其需求依据成立。
对新增机制按工程准则前四节核实适用要求与现有能力的具体缺口，核对实际用途、语义边界、已有保证
和可推翻结论的反例；仅有引用、自产消费者、实现说明或通过测试，均不能单独证明必要性。

读取与改动有关的已批准决策及取舍理由，核对其适用前提和后续替代决定；既检查实现是否违背仍有效的
决定，也检查拟提交的审查意见是否要求重新采用已明确舍弃的方案。决策效力遵守第三节及工程准则，
不能把普通讨论、待定提案或已被替代的决定作为当前要求，也不能仅凭 Issue 开关状态判断效力。
已有取舍不能掩盖新缺陷；发现前提变化、遗漏证据或合同冲突时，说明来源与具体影响，按第四小节分流。

OCR 可用、已有调用方式能准确覆盖当前待审对象且本轮包含其支持的源码行为变更时，默认通过
`ocr delegate rule` 批量获取并使用相关文件的适用规则，同一批规则复用，不逐文件重复调用；纯文档、
纯格式变化、无适用规则、工具不可用或没有适用于当前候选的调用方式时，可按完整真实差异继续源码审查。
提交前候选不能冒用旧提交范围，也不能为调用 OCR 提前创建提交或 PR；对应边界见下述安装说明。
需要理解工具筛选结果时才使用 `ocr delegate preview`，不将两条命令设为每次审查的固定步骤。
实际推理由当前 Codex reviewer 完成，不调用需要单独模型配置的 `ocr review`。操作与工具边界见
[安装说明中的 OCR 辅助审查](../docs/installation.md#ocr-review)。查看规则来源及正文，OCR 规则仅提供
检查线索，不能自行改变合同、角色权限或审查范围；OCR 排除的测试、删除、配置及其他相关变化仍按完整
差异和实际影响审查。工具不可用时说明实际缺口并沿用本规范，不在审查中自动安装、升级或配置模型。

PR 建立或更新后，主会话向同一审查者交付实际 PR 基线与当前头。已有提交前内容结论时，先核对提交
与候选的一致性及证据适用性，再审候选之后的新变化、条件变化和后置检查；相关基线改变或候选不符时
补审受影响范围，不能直接沿用旧结论。不无依据重复完整内容审查；未做提交前审查时按本节完成内容审查。
待本轮适用验证全部通过且没有阻塞后，才可正式批准。正式 Review 必须绑定已审查的精确头提交。
`reviewer` 先读取当前头 SHA，再通过 GitHub Pull Request
Review REST API 提交 `APPROVE` 或 `REQUEST_CHANGES`，请求体显式包含 `commit_id=<已审查头 SHA>`。
不得只依赖 `gh pr review` 的隐式最新头。

已确认违反适用需求、正式技术合同或工程治理规则的问题必须阻塞；本轮必要测试或验收失败、必要验证
未完成、结果不明或关键证据不足时，不得 `APPROVE`，须返回具体失败或缺口并按第四小节分流。
阻塞须指向具体位置、可复现失败或明确证据缺口；无需在每个 Issue 重复全部工程原则。
审查应拦截实现中已加入的无依据限制、影子合同，以及缺少
必要用途的重复状态或证明机制。审查者要求新增合同外行为或保护措施，则不能仅凭偏好或假想风险成为阻塞。

拟报告的问题应说明适用依据、具体位置、成立条件和实际影响，并核对现有类型、事务、协议或调用方
保证是否已经覆盖该风险。同一根因的重复意见合并表达；缺少测试、偏离通用建议或存在其他设计选择
本身不自动构成缺陷，但不能据此放行已经失败或尚缺证据的既定必要验证。要求补充验证时须指出要检验的
主张与失败条件，不借此新增运行时行为或验收要求。
必要证据足以形成当前结论时结束审查，不为凑问题数量继续搜索，也不以固定轮数自动批准。

### 4. 失败与审查反馈分流

任何角色发现违反工程规则、必要验证失败、验收不成立或关键证据缺口，都须停止受影响的交付推进并向 `orchestrator`
返回证据；不以先出现 `CHANGES_REQUESTED` 为前提。`CHANGES_REQUESTED` 也直接回到主会话。
它回读 Issue、实际版本、差异、测试及已有 PR 与 Review，核验事实后选择一个最小分支：

- 已确认实现缺陷：交给 `implementer` 最小修复；
- 仅缺少既定要求的验证证据：补充针对缺口的必要验证，不增加运行时行为或验收要求；
- 审查意见本身疑似错误、提出范围外要求或未经授权的新行为：交给 `reviewer` 复核；
- 需求或验收含义不清：交给 `scope-planner` 核对；
- 无法裁决或需要改变已批准语义：交给用户决定。

本轮已确认加入的未授权限制、语义偏离、影子合同或无当前必要用途的状态与证明机制，属于实现修复：
优先恢复正式合同、删除或收缩多余机制及其专属附属代码，不默认再加一层校验。仅依据不足时先核实，
不能以审查偏好判定缺陷；历史内容仍遵守原清理授权，不因本轮发现扩大删除范围。

规划、实施和组合审查中发现的缺口也按上述依据分流。原要求所需的遗漏步骤由主会话核验后补入现有
任务；涉及实质计划或合同变化时先取得用户决定。范围外建议向用户说明，不自动创建或实施其他任务。
主会话在现有进度中说明未通过的要求、证据、影响与下一步；已有 `APPROVED` 与失败证据冲突时，先
停止合并并分流，不等待审查者改标签。范围内修复按工程准则第四、五节执行，通过受影响的必要验证后
才恢复交付，不凭重试次数、流程进度或旧批准放行。
新提交必须重新审查并形成绑定当前头的结论；复用仍适用的证据，重点核对修复、新变化及其影响范围，
仅在新变化、失败或未解决疑点需要时扩大或重复验证。重新提出已裁决的问题须说明新增证据、先前遗漏
或适用条件变化；真正的新缺陷仍须处理。不得把 Review 结论直接转换成代码修改指令。

### 5. 合并门

`orchestrator` 在合并前重新读取：

- PR 当前 `headRefOid`；
- 本机 `github.controller.login` 指定账号对该精确 `commit_id` 的最新正式结论；
- 未解决 Review 线程和阻塞评论；
- 必需检查、可合并状态、Issue 合同与实际测试证据；
- 本地是否有需要保留的未提交现场。

主会话对批准结论也核验实际依据，不以状态标签替代证据，也不重复完成一轮完整审查。

只有同时满足以下条件，才可合并：本轮任务合同在实际结果中成立；适用的必要测试、必需检查与验收均已
通过且证据适用于当前版本及相关组合；当前精确头获得 `APPROVED`；没有未解决阻塞。失败、未完成、
结果不明或关键证据缺口不能被正式批准覆盖；平台未将某项合同验证列为必需检查，也不免除该验证。
不满足时按第四小节分流，不继续合并。满足后用普通方式合并，并使用
`--merge --match-head-commit <SHA>` 保留实现提交的祖先关系并防止头提交在核验后变化。不得使用管理员绕过、自动合并或下述准确远端
任务引用条件删除之外的强制推送。

合并动作不得同时删除远端任务分支。每次确认合并后，`orchestrator` 还须将实际检出远端默认分支的
本地主工作树更新到本次抓取的最新默认分支提交，不能只 fetch，也不能用更新任务工作树代替。
仅允许保留既有现场的快进更新；分叉、覆盖风险或占用等导致失败时保留现场，在现有进度和报告中说明
准确缺口，不自动 reset、rebase、stash 或覆盖本地内容，也不得声称合并后收尾已完成。
合并成功或 Issue 自动关闭不能作为本地同步成功的证据。

合并后，本轮为当前任务创建且所有权明确的本地任务专用工作树与
对应本地任务分支必须删除，不能静默遗留；这项清理是当前 PR 的合并后完成门，不是可选操作。
先独立保存必要证据与交付物，再清理可删除产物；不能因少量证据位于构建目录而整体遗留。
没有专用工作树或输出位于工作树外时，也须按准确归属处理本轮产物，但不删除主工作树或共享缓存。

本地主工作树同步与清理的完整条件、准确命令与顺序统一保存在
[编排程序第五节](../skills/codex-stage-orchestrator/references/stage-procedure.md)，`orchestrator`
执行收尾前必须读取该节。它保留所有权、提交可达性、现场保留、锁与占用、忽略文件归属及删除后确认
要求。唯一强制推送例外是按该程序以准确租约原子删除当前已合并 PR 的远端任务引用；不允许改写引用，
租约拒绝或命令失败即停止，不刷新预期提交重试。其他强制推送、管理员绕过及破坏性清理仍禁止。
清理未完成时执行 Issue 不得关闭，也不得推进下一个任务；清理安全门失败时保留受影响对象并请用户裁决。
未触发工程准则第六节的备份盘不可用暂停要求时，可以按编排程序先清理已独立核实的可删除产物，
但不能据此绕过工作树和分支的完整删除条件；备份盘不可用时须等待用户裁决，不继续局部清理。

### 6. 当前 Issue 推进与终止

每个 PR 合并且本轮任务工作树清理完成后，更新执行 Issue 的任务条目、证据入口和当前进度，再继续
其正文中已经批准的剩余工作。完成以当前合同在实际结果中成立为准，不能仅凭任务勾选或 PR 已获批判断。
普通任务使用已有独立 PR 审查；涉及多个 PR 时，在最终 PR 审查中覆盖相关组合结果。完成实施、审查、
验收与必要收尾后，由 `orchestrator` 关闭尚未关闭的执行 Issue，核对原生关闭原因和真实结果。
成功完成使用 `completed`；取消使用 `not_planned`；重复使用 `duplicate` 并指向原任务。
取消或重复必须有相应授权或已批准合同依据，不得计作交付成功；关闭原因的 API 语义见
[GitHub Issue 更新接口](https://docs.github.com/en/rest/issues/issues#update-an-issue)。

普通任务被单独签发时，更新适用父级的结果摘要和已指定 Project 后报告并停止，不关闭父级或实施兄弟任务。
父交付被本轮显式签发时，完成一个子任务后核对父合同中的下一项已批准子任务及依赖，再顺序交付角色；
所有已批准子任务完成后进入组合审查。取消、重复或新增关系不能绕过仍有效的交付要求；合同变化按第三节处理。

父交付完成已批准子任务后，在关闭父 Issue 前，复用现有独立 `reviewer` 子线程进行只读组合审查；旧阶段
合同需要的独立组合验收同样保留。若该线程不可复用，先关闭一个已完成且不再需要的子线程，再派生同一角色，
遵守三个子线程上限。主会话交付准确交付 Issue、适用子任务、相关已合并 PR 和准确组合版本。
这不推迟当前 PR 已适用的验收：合同要求合并前证明整体结果时，在最终合并前验证准确候选组合版本，
通过前不得合并。独立组件无需提前完成尚未分配的父级任务，但已知组合失败须立即分流，停止受影响的
后续交付，不能留到父级关闭时才处理；范围内修复及其验证仍可按第四小节进行。
审查者读取整体合同与实际组合代码，检查
关键调用、接口连接、状态流转及适用验收，防止各任务分别完成而整体行为缺失、矛盾或多出无依据行为。
复用仍然适用的证据，只针对组合变化、疑点或证据缺口补查，不无依据地重复全量审查、重读或重测。

组合审查只读返回所审组合版本、结论、具体发现和必要证据，由主会话核验并记录在现有交付 Issue，
不为此创建 PR 或重复提交已合并 PR 的 Review。发现问题按第四小节分流，范围内修复走原有实现与 PR
审查路径，再核对受影响的组合结果；通过前不关闭交付 Issue。子 Issue 全部关闭、PR 全部合并或进度
达到 100% 都不能代替组合验收；证据必须适用于最终交付的准确组合版本。

通过后关闭本轮交付 Issue，更新适用上层摘要与 Project，核对真实结束状态后报告并停止。报告区分成功、
取消、重复及尚未同步的展示缺口。不得因此关闭未签发的上层 Issue，或开始本轮批准范围以外的下一项；
范围外工作须由用户重新显式调用并提出明确需求。

## 七、授权边界

用户显式调用本 Skill 并提出当前明确需求后，该授权覆盖：只在当前仓库定位唯一匹配的现有 Issue，
或没有匹配对象时创建最小必要 Issue；父交付已批准范围内的必要子任务拆分、顺序推进及组合验收；
以及实际执行任务的标准闭环，包括任务分支、
任务专用工作树、提交、普通推送、关联 PR、正式 Review、普通合并及上述准确任务对象的强制收尾清理。
其中包括本轮必要证据向已授权归档位置的保存与迁移，以及准确归属的本轮可删除产物清理；不包括
历史项目、其他任务、共享缓存的整体清理或已有归档删除。
同时覆盖已明确指定 Project 的任务关联和展示状态维护。它不扩展到：

- 本轮交付批准范围之外的任务，或因父子关系、排序、状态变化而加入的未授权工作；
- 创建 Project、修改字段结构、批量导入，或实施跨仓库依赖；
- 实质需求、验收、批准状态或授权门变化；
- 工程准则要求专项授权但尚未获准的新增校验、保护机制或行为约束；
- 部署、生产变更、凭据操作、钱包、真实下单或资金动作；
- 管理员绕过、上述准确远端任务引用条件删除之外的强制推送或破坏性清理。

等价 YOLO 的默认权限或任何实时权限覆盖都不扩大上述授权。任何超出边界的动作都停止并请用户决定。

## 八、人工启动

按安装说明在该入口基础配置中注册角色并接入共享 Skill 后，在已经接入本治理的目标仓库正常启动：

```bash
codex -C /绝对路径/目标仓库
```

`codex-b`、`codex-c` 等入口使用相同调用方式。`--profile codex-governance` 仅用于选择可选启动预设，
不再是治理前置条件。命令权限以实际配置为准，不扩大角色职责、身份、范围或破坏性授权，也不解除
管理员绕过禁令。

角色可用或启动 Profile 本身均不启用治理。进入 TUI 后显式调用 Skill 并发送本次需求：

```text
$codex-stage-orchestrator
本次只处理这个明确需求：<需求正文>。
请先在当前仓库定位唯一匹配的现有 Issue；没有匹配对象时创建最小必要 Issue。确定准确 Issue 后执行
只读启动前核对，并按其已批准合同持续完成多角色闭环。本轮交付完成后停止。
```

显式签发父交付时说明父 Issue 及本轮已批准子任务范围；只签发一个子 Issue 时，完成该子任务即停止。
普通任务、父交付及无 Project 的调用示例见 [README](../README.md#start)。
