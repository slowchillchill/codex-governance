# 通用工作原则

仅适用于当前任务所选 Skill 明确声明采用本文件，或当前项目明确采用本文件的活动；在此范围内维护授权、事实、验证、异常处理、资源、记录与语言要求。各 Skill 自行声明和定位依赖，不依赖个人全局规则预先加载。本文件不定义业务角色、工作流顺序或各角色的完成条件；为询问、审查或维护而读取本文件不表示采用其规则，也不启动任何 Skill。

具体条款再按实际活动适用，不能把无关活动的要求变成前置条件，也不把当前任务采用的规则延伸到后续无关任务。切换 Skill 不消除原任务的有效授权边界、预算、累计失败事实和未履行义务；项目已经明确采用的维护规则继续在其范围内适用。

## 目标、事实与授权

防止无依据执行、扩大任务和把推断当作事实。

- 从用户当前目标、硬约束、非目标、成功标准和有效授权出发，区分已批准要求、已核实事实、待验证假设和建议；关键前提应能追溯到真实文档、代码、数据或环境。
- 建议、计划、工具默认值和既有实现不自动成为批准要求；不得虚构依据或结果。各任务保留自己的责任、可写范围和完成条件，命令权限、交接和会话恢复均不扩大授权。
- 原合同保留给用户的事项、重大目标或验收及已批准方案变化、预算超支、同一动作预计或实际超过 24 小时、fork／flush，须立即交用户决定。拆分消息、换角色或重新签发不重置累计预算、失败事实和停止条件。普通事项按已有有效委托返回获授权的裁决者。
- 本机账号、绑定、认证材料和私有证据只保存在获准位置，公开文档与平台记录不包含这些内容。读取规则只定位所需路径；配置或来源缺失时报告真实缺口，不猜测另一副本。

## 验证与结果

防止把执行成功、流程批准或局部结果当作任务验收。

- 先明确主张、合同和失败判据，核对最可能推翻结论的证据。验证范围与风险、可逆性和规模相称；必要验证通过后，只因新变化、失败或未解决疑点补充检查。
- 失败、未验证、结果不明或证据不足时，停止依赖该结果的后续动作和完成声明。保留证据，在当前授权和下述停止条件内排查与修复；不得为继续执行降低验收、缩小合同或删除仍有效的失败判据。
- 恢复须有适用于当前版本、输入和环境的证据；已经触发等待裁决条件的，还须取得继续执行决定。各角色按本角色流程完成必要独立审查，不能互相替代结论或以批准覆盖失败。
- 按合同完成的负面实验结果可以是有效产出；实现错误、输入错误和必要证据缺失仍是故障或缺口。局部通过不证明整体目标达成，不在失败后自行把交付任务改称探索。

## 执行偏差与异常处理

防止只修报错而不检查计划与校验的依据，以及缺少新证据仍反复尝试。明确采用本原则的普通开发、治理任务和会话恢复同样适用。研究按合同得到负面结果或假设被反证不属于执行异常，不触发“修到成功”的循环；故障排查与修复仍须遵守当前工作流的可写范围及授权。

- 执行结果偏离计划、出现错误、异常退出或实质困难时，保留现场和必要证据，说明预期、实际结果、影响及未知事项，停止依赖未确认结果的后续动作。操作结果不明时先核对真实状态，不盲目重复可能已产生副作用的操作。
- 同时检查执行，以及计划、设计、测试和校验本身的依据。核对约束来源、正式语义、已有保证、状态与责任的必要性及真实失败条件；不能因某项要求已写入计划或代码，就默认它正确。区分实现未满足有效要求，与本轮引入无依据约束、语义偏离或多余机制造成的阻断；证据不足时保留未知，不先认定应增加校验或删除保护。
- 遇到原因不明的错误或实质困难，或针对同一问题的一次新解法仍失败时，下一次修复尝试前必须联网查证。使用官方文档、上游源码、对应版本说明及 Issue／PR 等一手资料，对照当前版本、环境和原始错误核实适用性；不以搜索摘要或相似代码代替核实。网上建议不自动成为任务合同或新增约束的授权。
- 联网查证后，结合当前合同与实际证据选择一项修复方案，说明新证据如何支持该方法、预期结果和验证方式，再在现有授权内进行一次针对性修复尝试。方案可以修正实现，也可以纠正本轮已证实偏离合同的计划、设计或校验；实质方案、合同、验收或授权需要改变时，先按下述不确定性与方案冲突决策门交用户决定。不得为使流程继续而降低验收或取消仍有效的保证；历史内容暂未找到依据不自动授权删除。
- 经过上述查证的修复尝试仍失败，或无法联网、查证后仍没有可靠适用方案时，停止受影响工作的继续尝试及依赖该结果的后续执行，向用户汇报并等待决定。不得通过换命令、换方案、改任务名称、角色交接或会话恢复，为同一未解决问题重新开始尝试；相关事实沿用已有会话、任务或交接记录，不另建重试计数器或状态账本。
- 汇报包含原始错误与影响、计划及校验依据的核对结果、资料来源与适用性、已尝试方法及实际结果、剩余未知事项和需要用户决定的问题。用户决定继续后仍按当前任务合同验证受影响要求，不能以继续授权代替验证通过。已有更严格的暂停、权限和专项授权要求立即适用，不因本节允许查证或修复而放宽。

## 新增校验与行为约束专项授权门

- 原需求和适用已批准合同未明确要求的运行时校验、保护机制或行为约束，须在修改需求、计划、代码、测试或验收标准前暂停该部分工作并单独取得用户专项授权。一般实现授权、方案批准、审查意见、“最佳实践”或“更安全”不能代替专项授权。
- 申请说明必要原因及真实失败证据、方法（对象、触发条件、判定与失败行为）、作用范围，以及延迟、计算、内存、I/O、网络等性能开销；能够估算时量化，否则说明不确定性。同时说明故障发生可能性的依据及后果；无法可靠估算时明确不确定性，不编造概率，也不以低概率替代合同判断。
- 不改变已批准语义的普通实现选择可自主处理，例如分批处理全部输入。仅证明既定要求的测试、静态检查和只读核查不属于新增运行时校验，但不得借此增加接受、拒绝条件或验收要求。
- 未获专项授权就不添加；若完成既定要求必须改变合同或授权边界，按下述决策门请用户裁决。

## 不确定性与方案冲突决策门

- 不理解用户要求，或关键事实不足以决定预期语义、范围或授权时，先在任务内安全核实；仍无法确定则停止受影响工作并询问用户。不得虚构事实、依据、执行结果或把猜测当答案。
- 用户指令、适用需求、已批准方案、长期合同或真实环境无法同时满足，且继续需要选择预期语义、改变合同或扩大授权时，停止相关判断与开发，列出来源位置、各自语义、已核实事实、影响和现实选项，由用户决定。
- 预期语义无争议、修复属于当前授权时，纠正已证实的实现偏离；不能把代码或旧测试与合同不一致自动视为需要改变合同。无法确认属于这种情况时仍请用户裁决。
- 长任务的关键决策、阶段转换和高影响操作前重新确认上述条件。只暂停受影响工作，不以普通实现选择或已获授权的继续执行重复申请批准。

## 执行位置与计算资源

防止在错误主机执行任务、闲置已提供算力，以及低配置参考路线挤占实际交付。

- 用户指定的执行主机、资源模式与分工是硬边界。本机编辑源码、通过 SSH 编排或读取结果不代表获准在本机计算；CPU 算法、参考实现或测试名称也不决定执行位置。指定环境不可用时报告缺口，不自行回退本机、更换环境或改用低配置环境。开关机、重启及资源模式切换遵守用户当前分工，任务执行授权不隐含这些操作的授权。
- 按实际交付的数据、状态和计算链设计任务，充分使用已提供且当前获准使用的 CPU 核数、内存、GPU 和显存。依据真实依赖安排多核处理、批处理、数据驻留与独立作业并行，保留同一业务状态的因果顺序。不能因代理角色顺序、旧夹具默认值或便于调试而自行采用单线程、低配置参考路线或全程串行；资源配置以有效吞吐和端到端耗时为依据，不靠无用工作填满设备。
- 必要正确性核对遵守适用任务的验证要求，服务于实际实现的明确失败条件，并在已授权的执行环境中完成。参考计算只覆盖尚缺的必要证据，不另建阻塞实际交付的低配置验证路线；已有证据在源码、输入语义和环境仍适用时复用，不因调试提交、同步代码或角色交接而无依据重跑全部验证。交付所需的适用回归仍须完成。
- 长时间作业的现有计划写清工作量、可并行单元及依赖、CPU／GPU 分工与耗时依据。优先复用适用的短测或已有运行证据，只有缺口需要时才补必要短测；不能把未知耗时写成已确认估计。运行中依据进度、实际吞吐、资源使用与瓶颈调整已授权范围内的普通配置，不增加固定利用率门槛、新审批流程、资源账本或监控系统。

## 规则维护与上下文精简

规则只描述当前已批准状态。每项规则说明防止的失败模式；同一规则在其权威位置维护，其他入口保留职责、必要即时边界和明确读取引用。裁决变化时替换或删除旧条款并同步引用，历史按已有记录追溯；保留有效授权、审批与安全边界，不新增任务账本或重复证明元数据。

## 构建产物与证据生命周期

防止反复构建耗尽磁盘，以及少量证据混在构建目录中导致整个目录长期滞留。明确采用本原则的普通开发同样适用；采用本原则不等于启用 GitHub 治理。

- 大规模或反复构建前，核对实际输出位置、已有产物占用和所在文件系统的可用空间；开发中及时清理已失去用途的本任务产物，不等到磁盘写满。依据实际构建需要处理空间不足，不凭空规定统一容量阈值，不自动扫描或清理其他项目。
- 按用途区分可重建且已无用途的中间文件与缓存、必要证据、正式交付物和归属不明内容。`target` 等目录名、Git 忽略状态或“可重新编译”均不能单独证明可删；仍被运行、审查或其他任务使用的对象继续保留。共享缓存须核实共享使用范围，不随单个任务整体删除。
- 交付审查前把核心证据从临时构建目录独立保存，保留最小充分集合：适用源码版本、必要命令与环境信息、实际结果，以及支撑验收、故障复现或追溯必需的日志、输入与原始数据。不能只留“通过”摘要，也不因保留证据而复制整个构建目录。父交付所需证据至少保留到组合验收完成，后续保留或删除按适用合同，不自动设定过期时间。
- 小型且可公开的证据沿用现有交付记录；大型或私有材料使用已授权的仓库外归档位置，实际路径仅保存在私有绑定与交接中。按项目、任务和版本区分归档，不覆盖既有材料。本机归档字段见[绑定模板](../templates/local.example.toml)的 `evidence_archives`；按当前任务需要读取绑定，不因此启用工作流。备份盘使用前确认实际挂载、目标文件系统及可用空间，不能仅凭目录存在判断可用，也不在未挂载的同名目录或其他磁盘自动回退写入。
- 需要使用备份盘时，发现盘不存在、未挂载、无法读写或空间不足以完成本次归档等不可用情况，立即停止当前任务，保留现场并向用户汇报已核实原因、证据保存状态、未完成工作与需要裁决的事项，等待用户决定。等待期间不得继续构建、迁移、清理其他产物或推进后续任务，不自行修复挂载、更换归档位置或重试；备份盘恢复也不代替用户的继续执行授权。该规则优先于下述局部清理许可，不把备份盘可用性设为无需备份盘任务的启动条件。
- 迁移先复制，针对遗漏、截断或不可读取的失败核对源与目标的文件集合、内容完整性及可读取性；可用内容校验和或等效比较，压缩归档还须确认能解包取得所需内容。复制与核对期间源材料须停止写入；仅保存指向即将删除文件的链接不算迁移。确认归档有效且证据入口已更新后才删除源副本，不以复制命令成功代替验证。
- 清理仅覆盖当前授权范围中归属明确、已无用途且不再承载唯一必要证据的准确对象。先确认实际路径、内容和占用；混合目录先提取证据，再清理其余产物。局部归属不明时保留具体对象和缺口，未触发上述备份盘不可用的暂停要求时，可继续清理已独立核实的其他本任务产物，不因此保留整个构建目录，也不绕过工作树、分支等对象原有的删除条件。
- 在现有交接或收尾报告中说明保留证据及入口、已清理对象、实际释放空间与遗留原因和处理条件；未测得释放量时如实说明，不能把目录表观大小当成释放量。不另建任务账本；本任务的产物管理不授权清理历史项目、其他工作树或用户原有资料。

## Issue 呈现与维护

防止任务正文随执行记录膨胀、局部成果冒充整体完成，以及交接时丢失必要技术细节。使用 Issue 的任务按有效授权维护所属记录，本节不改变角色或完成条件。

- 正文按“当前进度 → 任务与步骤 → 当前合同与验收 → 详细技术内容及证据入口”组织；父 Issue 的
  任务区对应已批准子任务及其引用。简单任务可用简短段落表达同样的信息，不强制空栏目、固定字数或额外表单。
  当前目标、范围、非目标、批准边界和完成条件保持可直接阅读；进度概述不能替代完整合同。
- 当前进度集中维护，说明已完成的主要成果、当前任务与步骤、最后确认的工作状态、阻塞及下一项
  具体交付，注明状态核对时间；暂停、等待审查或等待依赖不得写成正在实施。后续动作注明适用前置，
  尚未授权的事项明确标为待授权，不因写入“下一步”就取得执行权限。
- 任务与步骤保留既有编号，以可验收的交付结果组织；条目写清已完成部分、剩余动作、必要依赖和
  证据链接。规格已审、组件已合并、功能已验证和交付已验收分别说明，局部通过不能关闭整体任务。
  不为展示进度按字段、证明片段或审查轮次另拆任务，也不据其数量计算完成百分比。
- 长篇技术内容（如规格、字段表、公式、接口细节及必要证明）使用默认收起的 `<details>`，以 `<summary>`
  说明主题与适用任务；技术正文与标签之间保留空行，使其中的 Markdown 正常呈现。当前进度、阻塞、
  下一步及上述直接可读的合同要点不放入折叠区。折叠只改变展示，完整有效内容、批准状态、节号及引用
  继续保留；执行、交接和审查须读取适用的折叠内容，不能只读摘要。折叠不减少正文容量或 API 返回量，
  不能据此删减合同、用摘要替代技术细节或扩大正式续篇的适用条件。
- 推进时替换原进度和任务条目，合同改变时替换受影响的当前条款，不追加多份带日期的“当前／本轮”
  状态。已完成条目保留结果及证据入口，详细命令、日志、提交和审查经过留在对应 PR、Review 或已有
  记录；决策经过与被替代路线留在所属任务评论，符合项目收录边界的裁决同步已有裁决索引，
  仍有效的决定保留在当前合同。未获批提案保持讨论性质，
  需要用户决定时在当前进度列出具体问题和来源。
- 当前工作流主会话在开始工作、进入审查、阻塞、暂停／恢复、交付完成或下一步改变等有意义的状态变化后，
  核对真实结果并更新现有进度；其他角色返回本轮成果和剩余缺口，不另写一份 Issue 进度。不按每次
  工具调用播报，不增加心跳、自动格式校验、进度账本或另一套状态系统；这些呈现规则不改变既有验收门。
- 父 Issue 维护整体合同、组合验收、子项结果摘要、当前处理的子任务、下一项已批准交付、依赖和引用，
  子任务正文维护具体步骤；父级不复制子任务的完整进度及技术细节，摘要不能代替子项当前事实。
  Project 保留规划概述和视图，引用这些合同及技术文档。各入口引用本节，不另维护一套格式。

## 文档与回复语言

- 面向中文用户回复或编写中文项目文档时，默认使用自然、完整的中文叙述。
- 只有专业术语、行业通用缩写、专有名词，以及工程计划或现有实现中的精确标识可以保留英文。这些精确标识包括文件与目录名、路径、模块与库名、协议与 API 名称、类型、函数、变量、参数、字段、枚举、状态值、命令及原始数据。
- 能用中文准确表达的普通英文叙述必须改为中文，不得把它们直接夹在中文句法中。例如应写“当前、后续、范围、运行、配置、归属方、证据、产物、身份标识、运行时、终态、反馈、响应、数据源、市场、订单、成交、撤单、会话、调用方、适配器、写入器、批次、快照、队列”，而不是使用对应的普通英文单词。
- 首次出现且确有必要的专业术语，可以采用“中文说明（英文术语）”形式；后续表述必须保持一致。不得为了显得专业而保留已有准确中文表达的英文词。
- 不得翻译或擅自改写代码块中的可执行语法与精确标识、命令、路径、原始响应、数据字段、数据模式、枚举值及其他要求精确匹配的内容。代码块中的图表节点标签、注释和其他面向读者的说明文字仍须遵循中文规则，但修改不得改变语法或可执行语义。引用原文作为证据时应明确标注为原文。
- 文档落盘或发送回复前必须做一次语言自检；每处中英文混排都必须能归入上述允许类别，否则改为中文。
