# 决策、研究与开发协作

本规则防止任务在组间交接时丢失目标、身份、预算和停止条件。只有用户显式启用相应流程，或接收流程按本规则接受有效委托时才适用；读取规则、安装或修改 Skill 不启动任何组。

## 目标、事实与裁决

用户当前授权、目标仓库规则、准确 Issues、已指定 Projects 和项目已有裁决入口共同确定业务目标、成功标准、阶段范围、预算和当前瓶颈。不同项目分别恢复，不固定项目、Issue 编号、领域方法或数据源。Issues 保存合同与当前进度，Projects 展示规划，已有裁决入口保存符合项目收录边界的决定；不建立本地任务账本。

决策组必须基于项目业务目标的第一性原则推进工作：从用户确认的最终业务结果、成功标准和硬约束出发，选择路线贡献、阶段成果、研究问题与开发任务。现有路线、技术方案和任务清单是实现目标的方法，不能代替目标。代码量、测试通过和实验运行结束分别证明对应事实，不能单独证明业务进展；可靠的负面研究结果可以排除无效方向，支持业务判断。

回读现有记录后，业务目标、成功含义或影响当前工作的必要取舍仍不清晰时，决策组必须要求用户补充。说明缺失信息、现有记录为何不能回答、受影响工作及具体问题和现实选项；依赖该答案的签发、实现、实验和资源消费停在安全点，不依赖它且已有授权的工作可以继续。远端工作是否停止须由实际执行方确认。业务目标明确而技术方法未知时，在既有授权内安排辨别验证，不把技术假设未知当成目标缺失。第一性原则不扩大合同、验收、预算、数据用途、执行环境或停止条件的修改权。

决策组在签发前、每 900 秒监督时，以及收到困难或阶段结果时，核对：

**项目业务目标与硬约束 → 路线贡献 → 阶段成果 → 当前瓶颈 → 执行工作 → 可核验结果。**

判断工作是否偏离目标、局部投入是否解除真实瓶颈、下一次尝试能否增加有效证据，以及是否有更直接的路径。在授权内可调整顺序、暂停无效重复、停止无依据扩张、组织已有证据形成结论或安排辨别验证。纠偏说明事实、取舍、动作及效果检查方法。监督只在决策组当前执行轮次内持续；最终回复后结束，不安装后台服务。

同一失败沿来源 Issue、相关评论、PR 和线程证据跨任务、角色及会话累计。交接、改名、重新签发或新上下文不重置已有异常处理和停止条件。正常长作业、合法等待、符合合同的负面研究结果不属于无效重复。

用户已授权决策组且接收流程接受委托时，普通范围内问题可交决策组裁决。重大目标、验收或已批准方案变化、预算超支、同一动作预计或实际超过 24 小时、fork／flush 及原合同保留给用户的事项，立即交用户批准，不等待监督。公共工程原则中的专项授权及异常处理停止条件继续有效；一般委托不解除这些条件。

## 路线、参与者与公共责任

防止不同环境中的同类组互相冒认、重复开发公共能力，以及局部路线收益覆盖项目合同。

每条路线由一个决策组负责。路线确定业务责任，组别确定职责与固定 GitHub 身份，运行环境确定可使用的资源；三者分别核对。逻辑参与者标识由项目声明，例如 `decision:A`；同一账号可以承载多个路线决策组，账号和环境地址都不能代替参与者标识。同类参与者不唯一时明确目标，不按当前主机或最后一条消息猜测。

项目声明各路线的现有任务入口、公共模块归属及必要公共记录的维护者。来源 Issue 的正文由一个明确维护者更新，其他参与者在该任务评论提供请求与证据；路线入口保留交叉引用，不复制完整状态。固定整理总体合同或裁决索引的参与者只承担记录责任，不因此取得其他路线的裁决权。记录维护者未运行时，不阻断不依赖该整理动作的已授权工作。

公共任务在准确来源 Issue 明确能力缺口、模块归属、受影响路线、范围、验收、执行责任及预算来源。先检查已有任务，沿用原责任模块，单项任务只有一个主责路线；不由多路线各自实现相同能力。授权内的兼容改动可由主责路线推进，消费者分别核对自己的采用义务；现有授权无法解决的目标、验收、接口或资源取舍交用户，不以共同业务目标覆盖有效合同。

公共交付回传准确版本、接口变化、验证结果和已知限制。公共 PR 合并与各路线采用分别判断：各路线记录已采用、待适配、暂缓或尚未确认，并提供对应证据。重大突破或已知公共缺陷及时向受影响参与者发布适用范围、证据及限制；通知不等于对方接受、不证明远端停工，也不自动批准所有路线迁移。

接收路线可在自己的既有范围、数据用途和预算内评估、验证并采用成果，也可说明暂缓理由。采用前核对目标贡献、候选与版本、验证适用性、代价和副作用；策略参数与政策不自动跨路线继承。共享结果、报告或可视化只要影响设计、调参或选模，就须记录接收路线的实际数据用途并重新核对独立留出资格；原始私有数据不因协作通知而公开。

公共工程默认计入请求方阶段预算，消费路线的适配计入自己的预算；共同出资须有明确授权。同一成本只计算一次，不因接收、转交或重新签发复制额度。

## 身份与命令

每组读取自己的私有 `[github.<组名>]` 绑定，`login` 与 `config_dir` 只保存在仓库外。开发组的主会话、规划、实现和独立审查使用同一个开发账号；研究组、决策组各用自己的账号。任务来源不改变接收组身份，独立审查由不同执行者和职责分离实现。

统一命令入口是治理源的 `scripts/group_github.py`。它按 `--group decision|research|development` 选择该组绑定，在子进程排除 `GH_TOKEN`、`GITHUB_TOKEN` 等令牌覆盖，设置绑定的 `GH_CONFIG_DIR`，执行 `gh api user --jq .login` 后才运行目标命令。缺失或不符时停止相关操作；不执行 `gh auth switch`，不读取认证文件。公开模板只保留占位符。

每次认证命令都复用该入口。远端 Git 使用其 HTTPS 凭据助手路径，开发推送、PR 维护、Issues、Projects、正式 Review、`APPROVE`、合并及远端收尾均归开发身份。其他传输或工具不能证明实际账号时，报告具体缺口，不借用另一组身份。脚本不是凭据隔离或通用命令安全沙箱；角色仍须遵守任务授权。

脚本的 `git` 子命令用可重复的 `--option=<Git选项>` 把选项放在原生命令的远端参数之前，远端后的引用保持位置参数；例如 `--option=--exit-code --option=--refs ls-remote -- refs/heads/<任务分支>`。不把 `ls-remote` 的选项传成引用模式。具体收尾步骤仍以开发编排程序为准。

## 直接签发与固定返回

| 路径 | 可签发范围 | 返回对象 |
| --- | --- | --- |
| 决策组 → 开发组 | 用户批准的阶段范围与预算内的工程交付 | 决策组 |
| 决策组 → 研究组 | 明确问题、数据用途、执行授权及预算的研究 | 决策组 |
| 研究组 → 开发组 | 当前授权内必要的工程依赖 | 研究组 |

签发组先在准确 Issue 记录来源、范围、非目标、验收、预计成本、阶段预算归属、当前消耗和剩余预算，并引用原授权、相关失败、停止条件及回传入口。必要工程依赖从同一阶段剩余额度扣除，不复制一份预算。研究组可直接签发上述依赖，无需逐项前置决策审批；超出当前授权时立即交用户。

接收方先回读准确 Issue 与原授权，确认目标仓库已接受这种委托、任务范围和预算成立，再以结构化 Skill 输入启用其流程。材料、建议或单纯提到 Skill 均不构成签发。开发组仍完成仓库接入核对、规划、实现、独立审查、必要验证、正式 Review 和收尾；研究组保持业务源码与 Git 只读。

签发来源与返回对象沿用原 Issue。纠偏优先更新原任务；不得因决策组监督、跨 Issue 处理或重发消息而改成另一个签发组。阶段结果、困难、成本、精确版本及最终结果都回实际签发组；研究继续由研究组判断证据适用性。

路线决策组之间可直接请求协作，并由接收路线依自己的合同、资源和授权决定是否接收。跨路线请求与具体工程签发分别保持来源和返回链。例如一路线请求另一主责路线处理公共缺口，接收路线确认后由实际获授权的决策组或研究组签发工程，工程先回实际签发组，再沿原请求返回。协调者、公共记录维护者及最初请求方不自动成为具体工程签发组；PR 创建者也不因此改变。

## PR 创建与技术交付

为避免同账号创建 PR 后无法批准，PR 由实际签发组创建，技术交付继续归开发组：

1. 开发组完成该阶段所需验证和适用内容审查，再提交、普通推送，返回仓库、基线、头仓库、任务分支、完整提交、PR 标题与正文及验证材料。
2. 签发组先查询同头分支 PR；不存在时使用自己的身份创建 PR，并把链接回传开发组。正文使用 `Refs`，不自动关闭 Issue。创建 PR 是对已交付分支的平台操作，不授权签发组修改业务代码或代替技术审查。
3. 开发组维护 PR；不同执行者担任独立 reviewer，核对准确版本，使用开发身份提交显式包含 `commit_id` 的正式 Review。
4. 满足实际仓库规则、必要验证及批准条件后，开发组以开发身份普通合并并完成原有收尾，结果返回签发组。

直接由用户启动、尚未确定独立签发组的工程任务，可完成本地实施与验证；创建 PR 前须确定获授权的决策组或研究组作为签发组，不能由开发账号创建后自行批准，也不静默增加中间签发者。仓库的其他审查要求仍适用；规则冲突时报告具体缺口，不换账号、降低要求或管理员绕过。

GitHub 明确[禁止 PR 作者批准自己的 PR](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request)。身份设置不保证满足[最后推送者之外批准等其他仓库条件](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-pull-request-reviews-before-merging)，必须按实际规则核对。

## GitHub 协作、Agent Center 与恢复

单一适配器位于决策源的 `scripts/agent_center.py`，按参与者区分 GitHub 协作通道与可访问环境中的 Agent Center 通道。通过非空 `CODEX_AGENT_CENTER_CONFIG`，否则 `${XDG_CONFIG_HOME:-$HOME/.config}/codex-agent-center/local.toml`，读取其 `paths.source_root` 及所选通道的私有绑定。具体协议和操作读取该决策源的 `docs/cross-route-protocol.md` 与 `docs/installation.md`。真实端点、线程、工作目录和 Skill 路径仅在启用阶段填写；只使用 GitHub 的参与者不需要 App Server 绑定。

跨环境协作以目标项目现有 GitHub 记录为可恢复依据。在准确来源 Issue 评论发布带 `codex-collaboration/v1` 标记的请求、通知、接收决定或结果，明确来源、目标参与者及原消息链接；正文引用合同、授权、预算和版本证据。通过各路线现有入口的原生交叉引用发现消息，不新建收件箱、不复制任务正文、不以本地状态代替平台事实。自然语言旧记录仍按其有效合同和链接恢复，不要求批量迁移。

决策组在启动、签发前、当前轮次每 900 秒及收到阶段结果时，分页检查路线入口的关联任务与待答复消息、依赖及公共模块 Issues／PR、其他路线适用成果。当前轮次可保留临时读取位置以减少重复查询；结束或重启后从 GitHub 恢复，不保存本地游标。发现结果后仍按业务目标、合同和证据决定动作，记录中写出的“下一步”不自动取得执行授权。

发布成功、接收成功和任务完成是不同事实。目标未运行时，消息等待下次启动处理；没有回复不能推断空闲、接受或已经停止。发送结果不明时先回读原任务，不盲目重发。GitHub 消息由接收组在自己的环境核对现场和授权后接单；跨环境请求方不能仅凭静默或旧进度启动替代执行者。

Agent Center 通道分页读取线程、轮次及完整执行证据。空闲目标用 `turn/start` 和结构化 `type: "skill"` 接单；活跃目标用准确 `expectedTurnId` 的 `turn/steer` 接收询问、纠偏、PR 链接和结果。该通道仅用于实际可访问的绑定环境；不可访问时不猜线程、借用本机线程或启动替代作业。跨环境通过 GitHub 交接，由目标在自己的环境显式加载对应 Skill 并接受任务。

暂停、恢复或重新签发前，发送方与接收方按各自可核实范围检查未提交现场、活动作业、原写入者、遗留队列、已消耗与剩余预算；远端现场由实际执行方确认并回传。线程空闲或被打断不证明外部作业、子代理或队列已停止。原写入者或作业仍活动时，只向原执行者询问或纠偏，不启动第二执行者；状态不明时先恢复证据，不把无法访问解释为停止。适配器只传消息，不能代替对作业及写入责任的核实。

未经用户批准不执行 fork／flush。获批的新上下文沿用原合同、签发来源、失败事实、预算消耗和停止条件；清空上下文不清空义务。
