# 跨组交接协议

本文件仅适用于参与双方明确采用本协议的决策、研究、开发三组委托，定义任务、消息、身份和结果的交接关系，不规定接收方内部步骤。普通子代理分工或其他 Skill 的交接不自动适用。参与方按各自 Skill 声明定位本协议，并采用[通用工作原则](common-principles.md)中适用的授权、异常处理与停止条件；内部流程仍由各自 Skill 定义。

为询问、审查、安装或维护而读取本协议不表示采用，也不启动业务流程。有效委托须由接收方按自身启用条件明确接受；共享协议不授予其他流程的职责。原任务授权、预算、累计失败和返回义务不因切换 Skill 或会话而重置。

## 签发、接受与返回

防止把材料当成任务授权，或在交接后丢失责任。

| 来源与接收方 | 可交付的任务 | 结果返回 |
| --- | --- | --- |
| 决策组 → 研究组 | 用户授权内的问题、数据用途、执行范围及预算明确的研究 | 实际签发决策组 |
| 决策组 → 开发组 | 用户批准阶段范围与预算内的工程交付 | 实际签发决策组 |
| 研究组 → 开发组 | 当前研究授权内必要的工程依赖，无需逐项前置决策审批 | 实际签发研究组 |

签发方在准确来源 Issue 保留原授权、目标、范围、非目标、验收、数据用途（适用时）、预计成本、阶段预算归属、已消耗与剩余额度、相关失败、停止条件及固定回传入口。引用现有合同与证据，不复制任务正文或另建账本。必要依赖消耗同一阶段剩余预算，交接不生成新额度。

接收方先回读准确 Issue 和原授权，核对目标项目接受委托、范围及预算成立，检查自己环境的现场，再明确接受或返回缺口。接受任务时以结构化 Skill 输入启用本角色流程；材料、建议、询问、通知和仅提及 Skill 都不是新任务授权。当前有效任务的状态查询、反馈和继续执行沿用原授权，不重做接单，也不扩大范围。

结果、困难、实际成本、准确版本和剩余义务固定回实际签发方。普通事项仅在已有有效决策委托范围内交获授权的决策组裁决；用户保留事项和专项授权仍按通用原则处理。监督、公共记录维护或代发消息不改变签发来源。接收方不替其他角色判断其研究结论、业务成果或工程验收。

## 路线与公共交付

防止把账号或运行环境当作业务参与者，以及重复签发公共任务。

项目声明路线、逻辑参与者、各自任务入口、公共模块责任和必要记录维护者。逻辑参与者如 `decision:A` 由项目定义；同一账号可服务多个参与者，不能按账号、当前主机或最后一条消息猜测接收者。来源 Issue 正文有一个明确维护者，其他参与者在评论提供请求和证据；记录维护权不授予其他路线的裁决权。

跨路线请求与后续工程签发分别保留原消息及返回链。接收路线按自身合同决定是否接受；具体工程由实际获授权的签发方发出，结果先回实际签发方，再沿原请求返回。公共任务先沿原责任模块核对已有准确 Issue，保持单项主责。请求方阶段预算承担公共工程，消费者自身适配计入自身预算；共同出资须有明确授权，同一成本只计算一次。

公共交付提供准确版本、接口变化、验证结果和限制；公共合并不等于各路线采用。消费者分别回传已采用、待适配、暂缓或尚未确认及其依据，并按自身合同核对数据用途和证据适用性。共享结果不自动批准其他路线迁移，也不授权公开私有材料。公共缺陷或重大结果通知相关参与者时明确影响、证据和限制；发送通知不等于对方接受或停工。

## 身份与平台接口

各组使用自己的私有 `[github.<组名>]` 绑定，任务来源不改变接收组身份；开发内部角色共用开发身份。实际绑定、账号和配置目录保存在仓库外，公开模板只用占位符。

认证命令通过治理源 `scripts/group_github.py --group decision|research|development`，按自己的组选择绑定。脚本排除继承令牌，设置绑定的配置目录并核验实际登录名；缺失或不符时停止相关平台操作，不切换全局账号或借用另一组身份，不读取认证材料。它不代替任务授权，也不提供操作系统隔离。

工程远端 Git 交付使用该脚本的 `git` 接口和开发身份；传输身份不可核实时报告缺口。原生 Git 选项通过 `--option=<选项>` 放在远端之前，引用仍放在远端之后。各组自己的命令和安装步骤在各自入口维护。

## 工程分支与 PR 往返

防止平台 PR 创建改变代码责任和结果归属。

1. 开发方交回已验证、已推送的仓库、基线、头仓库、任务分支、完整提交、PR 标题与正文和验证材料。
2. 实际签发方先查询同头分支 PR；不存在时以自己的身份创建，正文用 `Refs`，不自动关闭 Issue，再返回 PR 链接。该动作不授权签发方修改代码、提交、推送或代替技术审查。
3. 开发方按自己的交付流程处理 PR，并回传最终版本、验证、交付状态和限制；签发方按自己的职责判断结果及后续工作。

用户直接启动但尚未确定独立签发方的工程任务可完成本地实施与验证；创建 PR 前须确定获授权的签发方，不静默增加中间角色。PR 作者不能批准自己的 PR，其他仓库批准条件仍须核对；不借账号或管理员绕过。工程组的审查与合并步骤只在工程流程维护。

## 消息、现场与恢复

跨环境以目标项目已有 GitHub 来源任务评论和路线入口交叉引用交接。消息使用 `codex-collaboration/v1`，明确来源、目标参与者、消息类型、原消息和合同入口；路由标记不证明授权。发布成功、接受成功和完成是不同事实，沉默不证明接受、空闲或停工。发送结果不明先回读，不盲目重发。

暂停、恢复或重新签发前，发送方与接收方按各自可核实范围核对原写入者、活动作业、未提交现场、遗留队列与剩余预算，远端事实由实际执行方确认。线程空闲或被打断不证明外部作业已经停止；原写入者或作业仍活动或状态不明时，不启动替代执行者。恢复沿用原合同、来源、失败历史、预算和停止条件。

仅在需要传输时读取决策源 `docs/cross-route-protocol.md` 与适配器操作说明。决策源从实际安装的决策 Skill 真实路径定位；Agent Center 的通道源与私有绑定通过非空 `CODEX_AGENT_CENTER_CONFIG`，否则 `${XDG_CONFIG_HOME:-$HOME/.config}/codex-agent-center/local.toml` 定位。纯 GitHub 交接不需要远端 App Server。可访问的 Agent Center 只向明确绑定的参与者传递消息，活跃轮次使用准确 `expectedTurnId` 的 `turn/steer`；适配器不代替接收方的接单判断、现场核实和授权检查。
